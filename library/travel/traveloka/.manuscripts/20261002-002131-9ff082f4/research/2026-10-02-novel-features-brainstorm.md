## Customer model

These personas come from the brief’s Users and Top Workflows and the user’s stated goal. They are inferred research roles, not interviewed customers. Weekly use below means repeated work during active trip research; the brief supplies no observed usage frequency.

**Fixed-date flight planner**

**Today:** They use Traveloka’s flight search and offer details to compare departure times, return legs, prices and baggage. The observed interface supports this workflow, but a single result page does not compare several explicit date combinations.

**Weekly ritual:** Revisit a flight shortlist during active planning, checking whether alternative dates or different flight schedules improve the options.

**Frustration:** Comparing dates and schedule trade-offs requires repeated searches while preserving passengers, cabin, currency and the correct round-trip total.

**Family stay planner**

**Today:** They search Traveloka hotels with dates, adults, children and rooms, then open room offers to examine occupancy, breakfast, cancellation and payment terms.

**Weekly ritual:** Recheck suitable properties and rate plans while arranging an upcoming family stay.

**Frustration:** A cheaper displayed room can differ in occupancy, meal plan or cancellation terms; determining the price difference for comparable flexibility requires inspecting several offers.

**Travel-option research assistant**

**Today:** They prepare a reproducible shortlist from Traveloka results, retaining query context, source IDs, exact price units and booking links.

**Weekly ritual:** Retrieve matched-context alternatives and revisit earlier quote snapshots while a human decides.

**Frustration:** A later retrieval can change prices or policies, omit earlier offers, or fail access; these outcomes must remain distinguishable.

**1. Flight date grid — adversarial answers.** Weekly use is defensible for the flight planner’s repeated date comparison during active research, although its frequency is inferred. This is not one endpoint renamed: each cell coordinates the complete search/poll/authoritative-price workflow. Its leverage is agent-shaped output across explicit dated searches, including separate success, no-inventory, access-error and upstream-error cells. The closest killed sibling is **whole-month cheapest flight finder**, whose completeness claim is unsupported. Hand code must enforce a small search cap, preserve per-cell timestamps and expose result/polling limits; the lowest retrieved amount must be labelled accordingly. Its redirect names the surviving `traveloka-pp-cli flights shortlist`.

**2. Hotel stay grid — adversarial answers.** Weekly use is defensible for the family planner’s repeated stay-date comparison during active research, without claiming observed frequency. It coordinates multiple real hotel/room retrievals instead of mirroring one endpoint. Its leverage is a matched-occupancy date comparison with source price bases and room/rate identities retained. The closest killed sibling is **automatic best hotel weekend**, which adds an unsupported preference and duplicates the useful bounded operation. Hand code must cap the explicit stay list, retain unsuccessful cells, and disclose when returned room or rate identities differ across dates. Its redirect names the surviving `traveloka-pp-cli hotels flexibility`.

**3. Flight trade-off frontier — adversarial answers.** Weekly use is defensible whenever the flight planner revisits an active shortlist. It performs a cross-entity local calculation over source prices and itineraries; no single captured endpoint returns this frontier. Its leverage is the deterministic set of trade-offs rather than an invented recommendation score. The closest killed sibling is **safe-connection scorer**, which makes an unsupported safety judgment. Hand code must compare only identical query/currency/price contexts, retain all ties, and separate offers with missing dimensions. Its redirect names the surviving `traveloka-pp-cli flights date-grid`.

**4. Cancellation price difference — adversarial answers.** Weekly use is defensible for the family planner reviewing flexible room choices during active planning. It joins and pairs several source rate plans, rather than renaming room inspection or generic quote comparison. Its leverage is the service-specific room/rate-plan relationship and a mechanical price difference for otherwise matching plans. The closest killed sibling is **cancellation prose adviser**, whose semantic interpretation is unnecessary and unsafe for preserving source meaning. Hand code needs a small snapshot-model addition for exact pairing keys; it must use source cancellation classifications rather than infer them from prose, and report unknown or unpaired plans. Its redirect names the surviving `traveloka-pp-cli hotels date-grid`.

**5. Quote snapshot changes — adversarial answers.** Weekly use is defensible for the research assistant’s repeated checks of an active shortlist. It compares separate retrieval events and is not an endpoint wrapper. Its leverage is a local temporal join that distinguishes changed matched offers from offers present in only one retrieval. The closest killed sibling is **background quote watcher**, whose persistent process and alerts exceed scope. Hand code needs snapshot identity/context metadata; matching must require complete exact identity keys, treat changed or missing identities as unmatched, and never interpret “not returned” as sold out. Its redirects name the surviving `traveloka-pp-cli flights shortlist` and `traveloka-pp-cli hotels flexibility`.

The two date grids require `// pp:data-source live`; the three snapshot commands require `// pp:data-source local`, with a clear rejection of unsupported data-source modes. Local SQLite readers must invoke the generated unsynced/stale hint helpers, drain and close parent rows before follow-up queries, and preserve snapshot timestamps. Snapshot writes must use one transaction seam and propagate failures. Live coordinators must reuse the core session/configuration client, check HTTP status before decoding, and remain ordinary HTTP commands. All five require custom Cobra implementation and root wiring; none is justified as `spec-emits`. Every final Long Description references only surviving command names.
