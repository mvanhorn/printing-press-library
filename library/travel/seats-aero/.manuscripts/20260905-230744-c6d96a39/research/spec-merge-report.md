## 2. Schema changes

- **`Source` enum**: 22 → 26 values. Added `finnair`, `lufthansa`, `frontier`, `spirit`. Did **not** add `lifemiles` (brief flagged it as a stale/anomalous example elsewhere in vendor docs, not in the current 26-row Sources table — followed the brief's explicit instruction not to add it without live confirmation, which is out of scope here).
- **`CabinClass`**: unchanged (economy, premium, business, first).
- **`AvailabilityResponse` → `SearchResponse`** (renamed, shape unchanged): BASE's `AvailabilityResponse` was already `{data, count, hasMore, cursor}` — this is byte-for-byte CURRENT's `/search` 200 shape (verified against `search_get.json`; CURRENT has **no** `moreURL` field despite the task's shape-hint mentioning one as something to check for). Since it already matched, I renamed the single schema to `SearchResponse` and used it for both `/search` and `/availability`, per the task's "unify to one schema name if identical" instruction, rather than adding a redundant near-duplicate schema.
- **`Route`**: added `NumDaysOut` (integer, nullable). **Claim-vs-reality correction**: the task's prose states NumDaysOut is "present in nested Route objects inside search results, absent in /routes rows" — this is **contradicted by CURRENT's own extracted OpenAPI JSON**, whose `/routes` 200 response schema explicitly includes `NumDaysOut` (`{"type":"integer","default":0}`) at `paths./routes.get.responses.200...items.properties.NumDaysOut`. I trusted the extracted spec (the closer-to-ground-truth artifact) over the task's prose summary and put `NumDaysOut` on the single shared `Route` schema used everywhere, per the AGENTS.md convention that code/evidence wins over a contradicting claim.
- **`Availability`** (the `/search` and `/availability` row shape): rebuilt from CURRENT's inline schema plus the task's live-observation field list. 78 properties total:
  - Base: `ID`, `RouteID`, `Route`, `Date`, `ParsedDate`, `TaxesCurrency` (new — not in CURRENT's doc, added per task's live-observation instruction), `Source`, `CreatedAt`, `UpdatedAt`, `AvailabilityTrips` (nullable array of `Trip`; CURRENT typed as OpenAPI 3.1 `["array","null"]`, converted to `type: array` + `nullable: true`).
  - Per-cabin (×4 for Y/W/J/F): `Available` (bool), `AvailableRaw` (bool, new), `MileageCost` (**string** — confirmed by CURRENT's own schema, e.g. `"6000"`, not the integer BASE assumed), `MileageCostRaw` (number, new), `DirectMileageCost`/`DirectMileageCostRaw` (number, new), `TotalTaxes`/`TotalTaxesRaw`/`DirectTotalTaxes`/`DirectTotalTaxesRaw` (number, new), `RemainingSeats`/`RemainingSeatsRaw`/`DirectRemainingSeats`/`DirectRemainingSeatsRaw`, `Airlines`/`DirectAirlines` (string — CURRENT types `YAirlines` etc. as **string**, not the array BASE assumed), `Direct` (bool).
  - **Doubt**: the task's live-observation text types the `RemainingSeats` family as `number`, but CURRENT's own extracted schema types the base `YRemainingSeats`/etc. as `integer`. I went with the task's explicit "observed live today" instruction (`number`) over CURRENT's static doc, on the theory that live observation supersedes a possibly-incomplete ReadMe export — but flagging this because it's the one place the two sources disagree and I couldn't verify live (no API calls permitted). If wrong, changing `number`→`integer` on the 16 RemainingSeats-family properties is a one-line-per-field fix.
- **`Trip`** (now: one bookable itinerary from `/trips/{id}`'s `data[]`, not the whole response): added `AvailabilityID`, renamed `Segments`→`AvailabilitySegments`, renamed `Duration`→`TotalDuration`, renamed `Taxes`→`TotalTaxes`, added `AllianceCost`, `FlightNumbers`, `Carriers`, `MixedCabinPct`, `TaxesCurrency`, `TaxesCurrencySymbol`, `Cabin`. Removed nested `Route` and `BookingLinks` (moved to the new envelope, `TripDetailResponse` — see below).
- **`TripSegment`**: added `AircraftName`+`AircraftCode` (replacing `Aircraft`), `DepartsAt`/`ArrivesAt` (replacing `DepartureTime`/`ArrivalTime`), plus `ID`, `RouteID`, `AvailabilityID`, `AvailabilityTripID`, `CreatedAt`, `UpdatedAt`, `Source`, `Order` (present on `/trips/{id}` segments) and `Cabin` (present on `/live` segments instead of `Order`) — both kept as optional so one schema serves both endpoints.
- **New `TripDetailResponse`** (not in the task's explicit schema list, added out of necessity): `{data: [Trip], origin_coordinates: Coordinates, destination_coordinates: Coordinates, booking_links: [BookingLink]}`. CURRENT's `/trips/{id}` 200 response is this envelope, not a bare `Trip` — BASE's flat single-`Trip`-object response could not represent it.
- **New `Coordinates`**: `{Lat: number, Lon: number}` — used twice inside `TripDetailResponse`.
- **`BookingLink`**: field case changed from BASE's PascalCase (`Label`/`Link`/`Primary`) to CURRENT's lowercase (`label`/`link`/`primary`) — confirmed against both `/trips/{id}`'s `booking_links` and `/live`'s `bookingLinks` item shape (identical items, differently-cased *container* field name: `booking_links` vs `bookingLinks` — an inconsistency in the vendor's own API, not something I "fixed" since both are real).
- **New `LiveSearchResult`**: `allOf: [Trip, {TotalSegmentDistance, OriginAirport, DestinationAirport, Connections, Aircraft, Filtered}]`. `Connections`/`Aircraft` are left as untyped (`{}`) schemas because CURRENT documents them as untyped (OpenAPI 3.1 has no `type` key for either field) and no shape is inferable without a live call.
- **New**: `Destination`, `DestinationsResponse`, `RefreshRequest`, `RefreshResponse` (with nested `quota`), `LiveSearchRequest`, `LiveSearchResponse` — all built directly from CURRENT's schema, descriptions copied verbatim where CURRENT provides them.
- **Dropped `examples`**: CURRENT's ReadMe export carries large realistic example payloads on nearly every schema node. Per the merge rule ("drop `examples` arrays in favour of a single `example`"), I chose to drop them entirely rather than inline a representative `example`, to keep the generation-ready spec's size and diff-reviewability manageable. This is a deviation from the literal instruction (single `example` vs. none) — flagging it as a doubt. No functional effect: the generator does not require `example`/`examples` for typed generation, and `--validate` passed clean.

## 5. MCP intents — binding-language limitation confirmed

Per the task's contingency: the validator's binding-expression regex (`internal/spec/spec.go`, `bindingExprRe`) is
```
^\$\{([a-z][a-z0-9_]*)(\.[a-zA-Z0-9_]+)+\}$
```
This allows only dot-separated identifier segments — **no array-index syntax** (`[0]`). `find_best_award`'s intended step 2 (`bind: {id: "${results.data[0].ID}"}`) cannot be expressed. Per the task's explicit fallback instruction, I dropped step 2 and `find_best_award` is a single-step intent (`awards.cached-search`) that `returns: results`. An agent using this intent gets ranked cached-search results but must issue a separate `trips.get` call itself for bookable flight-number/time detail on its chosen result — documented here as the load-bearing limitation, not silently absorbed.
