## Customer model

### 1. The six-server founder
One Postmark account token, six product servers: Main App, Staging, Billing, Marketing Site, Docs, Support. Ships to several of them in a given week.

**Today (without this CLI):** Opens the Postmark web app and clicks into each server's Activity and Stats pages one at a time. The official CLI needs a different `POSTMARK_SERVER_TOKEN` per run (the eSolia backup Action keeps one secret per environment for the same reason), and the official MCP is one server per process. They cannot answer "which product sent less this week than it usually does" without eyeballing six charts, and cannot answer anything about a message older than 45 days because it has expired from the API.

**Weekly ritual:** A Monday pass over all six servers after the previous week's deploys: did each product keep sending, did bounces or spam complaints move, is anything unverified or failing (brief Top Workflow 6: "which of my servers is bouncing, which has unverified domains, where did sends drop").

**Frustration:** A product whose mailer breaks in a deploy does not bounce or error. It goes quiet, and a gap in one of six dashboards is easy to miss until a customer writes in. postmark.js #129 describes the same shape from the outage side ("some customers not receiving emails"), and the maintainer's answer was that detection and retry belong to the caller.

### 2. The support person answering "I never got the reset email"
Works a ticket queue for one or more of the products; copies addresses out of tickets into Postmark.

**Today (without this CLI):** Pastes the address into the right server's Activity search, then checks the bounces list and each stream's suppressions. MCP `diagnoseDelivery`, pmx `otp`, and agent-postmark `investigate delivery` all work one address at a time. Clearing a block means reactivating the bounce or deleting the suppression by hand (brief Users; Top Workflow 1).

**Weekly ritual:** Several missing-email tickets a week: look up the address, read the event timeline, reactivate or unsuppress, ask the customer to retry.

**Frustration:** When three tickets in a morning come from `@outlook.com`, or from one customer's company domain, nothing shows whether that mailbox provider is bouncing the product's mail as a whole or whether these are three unrelated cases. The brief's hygiene workflow already thinks in domains ("list inactive addresses by type and domain", Top Workflow 3), but the only domain-level tool in the ecosystem is a removal script (arnaud-coral/Postmark-Bounce-Removal) that deletes bounces by domain without reporting on them.

### 3. The developer who keeps templates in git
Promotes Postmark templates from a staging server to production, the official CLI's core use (brief Users; Top Workflow 2).

**Today (without this CLI):** `postmark templates pull` with the staging token, edit in a PR, `postmark templates preview` on a local Express server, `postmark templates push` with the production token. Some teams run the eSolia cron Action to commit pulls as a backup. Each template's test data lives only in the local `meta.json` `TestRenderModel`; Postmark never stored it (postmark-cli #29, open 5+ years).

**Weekly ritual:** Edit one or two templates or a shared layout in a PR, preview, push to staging, then production.

**Frustration:** Nothing checks the whole set before a push. A layout edit changes every template that uses it, a template without an alias is silently skipped by pull (official CLI source), and a new template variable that the test model lacks renders empty without failing anything.

### 4. The person who lets an agent send mail
Runs Claude or another agent with Postmark access to send follow-ups, receipts, and one-time codes on their behalf. The brief's User Vision asks for "the best agent CLI".

**Today (without this CLI):** The official MCP (server token only, one server per process, Markdown output, no retry) or pmx and agent-postmark with `--yes` write gates. To learn what the agent sent, they read its transcript or search Activity by recipient.

**Weekly ritual:** The agent sends dozens of one-off emails across the week; the person spot-checks that each went out once and landed.

**Frustration:** The agent hits an error or second-guesses an attachment and sends again. postmark-mcp #54: "it automatically resent the email. This could be problematic if you're sending one-off OTP emails." Postmark has no idempotency key, and none of the existing tools stops the second send.

**1. `pulse`: Pass 3 answers**
- Weekly use: yes. It is the six-server founder's Monday pass in one command.
- Wrapper vs leverage: leverage. It fans out three stats series across every server through account-token resolution and compares two windows; no endpoint returns change against a baseline.
- Transcendence proof: cross-server fan-out from one credential, local stats_daily history, and agent-shaped verdict rows (`stopped` / `dropped` / `spiked` with a `next` command such as `messages search-outbound --server Docs --tag <tag>`).
- Sibling kill: `servers compare`, which duplicated `overview`; only its change-over-time part survives here.
- Buildability: hand-code.
- Long-description validity: `overview` and `streams health` are absorbed rows 43 and 45; both survive with those names.
- Build notes: `// pp:data-source auto`; `mcp:read-only`. Resolve per-server tokens through the same config seam `--server` uses (not `os.Getenv`), and send the account token only to `/servers` and the server token only to `/stats` (sending both returned a live 401 on `GET /server`). Postmark omits days without stats, so fill zero days before comparing, or `stopped` never fires. Use EST day boundaries to match the stats API. `--by tag` reads local outbound_messages only. Use `--min-baseline` so the low-volume Main App server (28 messages) does not flag on noise. Under `cliutil.IsDogfoodEnv()`, cap to `--by server`. On the local path, call `hintIfUnsynced` / `hintIfStale` for stats_daily.

**2. `email send-once`: Pass 3 answers**
- Weekly use: yes. The agent sends daily, and every retry-prone send goes through it.
- Wrapper vs leverage: leverage. It combines a local ledger, Metadata stamping, and a `metadata_` search before the POST; Postmark has no idempotency key.
- Transcendence proof: service-specific content pattern (Postmark Metadata plus the `metadata_<key>` search filter make the key visible to any machine sharing the server) and agent-shaped output (`duplicate: true` plus the prior MessageID, exit 0).
- Sibling kill: `email receipts`, a wrapper once every key is findable through `messages search-outbound`.
- Buildability: hand-code.
- Long-description validity: `email send` (absorbed row 1) and `email batch` (absorbed row 3) survive, but both are generated endpoint paths marked provisional until the merged spec is generated. Re-check both names after generate.
- Build notes: `// pp:data-source live`; reject `--data-source local`. Side-effect rule: print the payload and dedupe decision by default, deliver only with `--send`, refuse under `cliutil.IsAnyHarness()`. The key is `--key` or a sha256 of the normalized to, from, subject or template, model, and stream. Check the ledger first, because outbound search can lag a fresh send. Convert the lookup `fromdate` to Eastern Time. Write the ledger row after the POST returns a MessageID, and treat a ledger write error as a command failure. Map ErrorCode 406 (inactive recipient) to a structured error that points at `diagnose`.

**3. `recipient-domains`: Pass 3 answers**
- Weekly use: yes for the founder's Monday pass; the support person runs it whenever tickets cluster by provider.
- Wrapper vs leverage: leverage. It joins four synced tables across servers; no endpoint groups by recipient domain.
- Transcendence proof: local SQLite join across outbound_messages, bounces, opens, and suppressions, spanning all servers and past the 45-day expiry.
- Sibling kill: `bounces clusters`, merged in as Type, TypeCode, and SMTP-status columns; also `suppressions spillover`, which had no demand evidence.
- Buildability: hand-code.
- Long-description validity: `diagnose` and `domains health` are absorbed rows 42 and 44; both survive with those names.
- Build notes: `// pp:data-source local`; reject `--data-source live`; `mcp:read-only`. Call the sync hint helpers for each of the four resources it reads. Drain first: scan each aggregate query into slices, check `rows.Err()`, close, then run the next query. The domain is the lowercased text after the last `@` in each Recipients entry. Report unique opens as a secondary column, since the per-message opens endpoint keeps only the first open.

**4. `templates check`: Pass 3 answers**
- Weekly use: yes, as a CI step on every template PR the developer opens.
- Wrapper vs leverage: leverage. `templates validate` is one template with no verdict; this fans out across every template and layout, diffs `SuggestedTemplateModel` keys against the stored test model, checks layout references, and returns a typed exit code.
- Transcendence proof: service-specific content pattern (Postmark layouts, the official `TestRenderModel` on-disk convention) plus agent-shaped pass/fail rows.
- Sibling kill: `templates drift`, which absorbed pull plus push `--dry-run` already cover.
- Buildability: hand-code.
- Long-description validity: `templates render` is absorbed row 30 and survives with that name.
- Build notes: `// pp:data-source live`; `mcp:read-only`. `/templates/validate` rides POST, so route it through the client's read path, or the verify harness will no-op it. Declare the check-failed exit code in `pp:typed-exit-codes`. `--dir` is an input path, not a write flag.
