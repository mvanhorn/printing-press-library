1. Why is mailbox identity verified only during token exchange? A swapped, restored, or misnamed token file can make profile A authenticate as account B later; if requests use `userId=me`, a plan whose SHA says A will mutate B. File mode `0600` does not prevent same-owner mix-ups. Runtime identity verification is required before every sync/apply/recovery path.

2. What governs `labels.create`, `labels.update`, and `labels.patch`? They remain among the 19 generated operations, but the folded confirmation, inverse, and recovery rules cover only memberships and trash. A create request that succeeds server-side but times out is not safely replayable; patch/update can rename or hide a label, with undefined undo and concurrent-change behavior. This leaves the required “create folders” feature outside the stated safety model.

3. The unsubscribe authenticity test is insufficient. “DKIM=pass present” in stored `Authentication-Results` can match an attacker-supplied header or the wrong one among multiple results, and it does not prove the passing aligned signature covered both unsubscribe headers, as RFC 8058 requires. A forged or unsigned one-click header could therefore trigger an external POST that was never authenticated as one-click, violating the hard contact constraint.

4. Where are the synchronization commit invariants and freshness requirement? Partial sync must exhaust every history page, apply fetched changes, and advance its high-water mark atomically; full resync must reconcile vanished rows rather than merely upsert results, and must explicitly include Trash/Spam if reports and undo-window calculations depend on them. Gmail warns that history retention can sometimes be significantly shorter than a week, making 404 full-resync behavior routine enough to engineer fully ([Gmail sync guidance](https://developers.google.com/workspace/gmail/api/guides/sync)). A crash after cursor advancement, or an incomplete full-resync reconciliation, silently produces incorrect summaries and cleanup plans. The design also does not say that `cleanup plan` synchronizes first or records the resulting mailbox watermark.

5. What evidence establishes that adding the `TRASH` label through `batchModify` is equivalent to `messages.trash`? Google documents a dedicated trash operation and says system-label application through modification is permitted only “under some circumstances” and is not guaranteed ([label semantics](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels)). If this assumption is wrong, the API may reject a chunk or leave messages in unexpected states while the ledger describes a trash operation. The existing probe that `batchModify` works does not establish this specific behavior.

6. There is no Gmail-call timeout, retry budget, or backoff policy. A hung connection can hold the single-instance lock indefinitely; uncontrolled retries on 429/5xx can turn an outage into a quota storm; and authentication-refresh failures can strand write-ahead intents in recovery. Idempotence makes some retries permissible, but does not decide deadlines, `Retry-After`, retry ceilings, or when an outcome becomes partial/refused. Those decisions must be deterministic for the typed exit codes to mean anything.

7. Why is a path-prefix Bash allowlist considered an execution boundary? If it examines shell text, a command beginning with the approved binary can append shell operators, substitutions, redirections, or a sibling executable sharing the prefix. That would bypass the structurally send-free binary and permit arbitrary third-party contact. Given the recorded headless guard failure, this boundary needs exact executable/argument enforcement rather than an unstated assumption about prefix matching.
