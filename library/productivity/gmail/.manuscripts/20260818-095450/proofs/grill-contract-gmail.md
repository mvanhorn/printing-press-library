--- BUILD DESIGN (what is being generated/built right now) ---
A Go CLI generated from Google's Gmail v1 OpenAPI spec PRUNED to exactly 20 operations before generation: getProfile; messages list/get/modify/trash/untrash/batchModify/attachments.get; threads list/get/modify/trash/untrash; labels list/get/create/update/patch/delete; history.list. All other operations (send, insert, import, drafts.*, settings.*, watch/stop, delegates, messages.delete, batchDelete) do not exist in the binary.

Auth layer: multi-account named profiles (per-profile token files, 0600), installed-app OAuth loopback flow, every profile requests exactly one scope (gmail.modify), consented-account verification (after token exchange, call users.getProfile with the new token and compare emailAddress to the profile's configured email; mismatch discards the token).

Data layer: local SQLite — message metadata (from/subject/date/size/labels/List-Unsubscribe headers/unread), sync via historyId cursor with expired-cursor (HTTP 404) full-resync fallback, senders aggregates, FTS.

Cleanup engine: `cleanup plan` (Gmail query → counts + samples → plan file with a token) → `cleanup apply` (requires the plan token; executes via batchModify [add/remove labels, add TRASH] in chunks; writes a mutation ledger with per-message inverse operations) → `undo` (replays inverse ops). `rules add/list/run` = named saved local recipes (query + action) replayed through the same plan→confirm engine as one merged preview; a daily unattended scheduled job runs `rules run --plan` (PREVIEW ONLY) and reports; applies happen only after the owner texts a confirm code, which is matched by deterministic daemon code (regex on the owner's actual message), never by the model.

Unsubscribe engine: `unsub audit` extracts List-Unsubscribe + List-Unsubscribe-Post headers from the local store, classifies each sender: RFC 8058 one-click (URL + List-Unsubscribe-Post: List-Unsubscribe=One-Click) vs plain-URL vs mailto-only. `unsub run` executes ONLY the RFC 8058 one-click class (HTTPS POST to the sender's URL), confirm-gated per batch, recording a ledger; plain-URL entries are surfaced with their URLs for the owner to click; mailto-only entries are surfaced as a list and never acted on. `unsub verify` later joins the ledger against fresh arrivals to report violators.

Novel commands (local-store reads): delta (checkpoint diff), storage report, sort suggest (majority-label stats → batchModify plans), trash report (undo-window countdown vs Gmail's 30-day purge), score (hygiene snapshots).

The always-on assistant invokes this CLI via a Bash allowlist that permits only this binary's path prefix; her own session-level guards (deterministic PreToolUse path hooks) are separate and already live.

--- ROUND 1 GRILL LOG (all 7 challenges FOLDED; design revised as follows) ---
R1-C1 (raw mutation subcommands bypass plan/confirm/ledger) → FOLDED: all generated raw mutation subcommands (messages modify/trash/untrash, threads modify/trash/untrash, batchModify, labels delete) are REMOVED from the CLI's command surface; the internal HTTP client retains the operations but they are reachable ONLY through the ledgered cleanup/labels/unsub engines. Single-item conversational ops become 1-id micro-plans through the same engine (auto-echo-with-undo at small size, still ledger-recorded). Read subcommands stay generated.
R1-C2 (labels.delete is permanent, breaks inverse claim) → FOLDED: labels.delete pruned from the spec surface entirely (19 ops now). Folder deletion is a desk task in Gmail's own UI. The inverse-op claim now applies only to label add/remove memberships and trash/untrash, which are genuinely reversible.
R1-C3 (unsub SSRF + incomplete RFC 8058 validation) → FOLDED: unsub run auto-executes ONLY senders passing ALL of: List-Unsubscribe-Post header equals "List-Unsubscribe=One-Click"; HTTPS URL; DKIM=pass present in the stored Authentication-Results header for an aligned domain; List-Unsubscribe host's registrable domain matches the From domain's registrable domain (org-domain alignment); DNS resolution yields only public unicast IPs and the connection dials the resolved IP (rebinding defense); no redirect following (a 3xx is a terminal result, recorded); no cookies or auth headers ever attached; POST body exactly "List-Unsubscribe=One-Click" form-encoded; 10s deadline; 64KB response cap. Anything failing any check is classified plain-URL or mailto (surfaced, never executed).
R1-C4 (crash consistency across mutation/ledger/report) → FOLDED: write-ahead ledger — intent row (plan sha, chunk id, ids, deltas) durably committed BEFORE each API call; label mutations are idempotent by Gmail semantics (re-adding a present label is a no-op), so recovery re-applies any chunk in state "applying" then completes it; a startup/`--recover` pass performs this reconciliation before any new work. Unsub POSTs: intent→result(code)|unknown; "unknown" is never auto-retried (not provably idempotent) — surfaced for the owner. Fault-injection unit tests required at the chunk boundaries.
R1-C5 (what a confirmation authorizes) → FOLDED: a plan is an immutable snapshot file (account, full frozen id list, exact label deltas, sample digest, created_at) named by its content SHA; the confirm token is a one-time nonce bound to that SHA with a 10-minute expiry; apply verifies file-SHA equals the bound SHA (an edited plan invalidates), consumes the nonce transactionally before executing, and refuses account mismatches. The phone-side confirm code is matched by deterministic daemon code as the entire owner message.
R1-C6 (undo vs concurrent changes) → FOLDED: undo is DELTA-based, never preimage-replay — apply records only the deltas it introduced (added X / removed Y per id); undo reverses exactly those deltas and, per id, verifies current state still carries the delta before reversing (a message the owner meanwhile changed is skipped and reported as a conflict, never forced).
R1-C7 (operational hardening absent) → FOLDED: apply/sync take an advisory single-instance lock (lock file beside the store); every command uses typed exit codes (0 ok / distinct codes for partial, refused, unknown-outcome); apply/sync emit machine-readable outcome JSON the invoking layer (the assistant's scheduled sweep, which already has ran-today catch-up, external dead-man's-switch, and exit-code-preserving invocation) consumes; the CLI never pipes its own status through formatters.
