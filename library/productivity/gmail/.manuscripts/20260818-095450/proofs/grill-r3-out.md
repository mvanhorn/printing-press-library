1. The frozen authorization can expand or drift at apply time. `threads.trash` and `threads.modify` affect every message currently in a thread, including messages that arrived after the frozen plan was confirmed. Even message-level plans can act on stale state because apply checks the local watermark, not Gmail’s current state. A new reply or an owner relabel between plan and apply could therefore mutate content never previewed. Require mutations to target only frozen message IDs and perform apply-time live state validation, with drift causing refusal or a new preview.

2. Nonce consumption and recovery do not yet form a complete crash-consistent state machine. The nonce is consumed before execution, while an intent row is written before each API call; a crash between those commits leaves a consumed confirmation with no recoverable intent and no permitted retry. Define an atomic transition from confirmed nonce to an authorized, resumable apply record, then derive every chunk intent from that record. Recovery must distinguish “authorized but no call attempted,” “call possibly attempted,” and “completed.”

3. `trash` followed by `untrash` is asserted to be a genuine inverse without evidence about Gmail’s label side effects. If trashing removes `INBOX`, category, or other placement labels and untrash merely removes `TRASH`, undo restores the message to All Mail rather than its original location. Prove behavior with API probes or ledger the observed pre/post label delta and restore only the labels actually changed, subject to the existing conflict checks. The trash-report countdown must also avoid presenting Gmail’s 30-day behavior as an exact purge timestamp unless that precision is documented.

4. The 20-minute time-based lock break can create concurrent writers. A long full resync, stalled filesystem operation, or apply exceeding its soft deadline may still be alive when another process declares the lock stale and breaks it; PID reuse makes a bare PID check insufficient. Use an OS-released advisory lock or validate process identity and liveness with a heartbeat. Never break solely because the timestamp aged while the holder may still be running.

5. The unsubscribe authenticity argument contains a cryptographic gap. `dmarc=pass` can result from SPF alone, while the mere presence of a `DKIM-Signature` whose `h=` lists the unsubscribe headers does not mean Gmail validated that signature. Duplicate header instances further complicate which values were signed. Correlate a specific Gmail-reported `dkim=pass` result to the exact signature covering the exact selected `List-Unsubscribe` and `List-Unsubscribe-Post` instances, or reject ambiguous/duplicate cases. Otherwise an unverified header can be classified as confirmed RFC 8058.

6. “Pruned before generation” is not yet a durable send-free invariant. A generator upgrade, stale generated file, unpruned regeneration, or generic request escape hatch could silently restore a send/settings route while the token authorizes it. Pin and hash the source spec and generator, test the final command/symbol surface negatively, and enforce an exact HTTP method/path allowlist at the transport used by this binary. CI should fail if any route outside the 19-operation set appears.

7. Full-category summaries introduce untrusted email content into the assistant’s model context, but the design has no deterministic control/data separation for prompt injection. A hostile message can instruct the assistant to invoke an allowed cleanup command; the exact-binary hook permits it, and small micro-plans apparently require no owner confirmation. Require deterministic proof of an owner-originated intent for every mutation, including one-item operations, and treat message bodies, subjects, headers, URLs, and generated summaries strictly as data. Also specify how “full-category summaries” obtain and bound message content—the described local store contains metadata, not enough content to satisfy that requirement by itself.
