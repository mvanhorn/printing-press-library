# Review findings for internal/cli/coverage.go

[MAJOR] FALSE ALL-CLEAR when --gaps-only runs without both dates. coverage.go:295-303: if the filtered slice is empty and flagGapsOnly is set, the human branch prints "no gaps: every date in range was fetched and returned rows" and returns nil. But the never-fetched walk (line 220) only runs when neverChecked (line 160) is true, i.e. both --from and --to were given. Run `mufap-pp-cli coverage --gaps-only --human-friendly` against a mirror holding one fetched date and 300 unfetched ones: no calendar date was ever checked, yet the user is told there are no gaps and no range was even supplied ("in range" is itself false). The correcting caveat at coverage.go:342-344 ("never-fetched dates need both --from and --to") is unreachable in this path because line 302 returns first. The command's entire purpose is distinguishing holes from legitimate empties, and this branch asserts the opposite of what it verified. Fix: gate the "no gaps" wording on neverChecked, and print the caveat before the early return.

[MAJOR] MISSING-MIRROR GUARD emits a different JSON shape than the command's success path, and drops the one answer it should give. coverage.go:176-182 returns `printJSONFiltered(cmd.OutOrStdout(), make([]coverageRow, 0), flags)` — a bare JSON array — while every other machine-path return (coverage.go:290-292) emits the coverageView object {from, to, never_fetched_checked, gaps_only, rows, summary}. An agent decoding the documented object gets a type error exactly on the empty-mirror path. Second, and worse: when --from/--to are set, "no data.db at all" is precisely the case where every calendar date in the range is never-fetched, but the guard returns at line 181/179 before the walk at line 220, so it reports nothing rather than the full hole list plus a summary with dates_never_fetched = N. The adjacent no-such-table path (coverage.go:196-201) handles the same user-visible state — nothing has been backfilled yet — correctly, by setting ledger = nil and letting the walk run; the two paths give opposite answers for the same situation. Compare panel.go:154-160, which returns its own view type (panelEmpty()) from the identical guard.

[MAJOR] DAILY CALENDAR WALK APPLIED TO MONTHLY-CADENCE RESOURCES fabricates never-fetched dates and corrupts the contract's headline count. coverage.go:220-233: the walk defaults to all seven keys (line 221 `scope := coverageKnownResources`) and steps one day at a time (line 226), but "monthly" and "allocation" are mirrored under exactly one month-end date per month — backfill.go:188 builds them via time.Date(cur.Year(), cur.Month()+1, 0, ...).Format("2006-01-02") and saves at backfill.go:564 and backfill.go:744. A fully mirrored monthly resource therefore reports ~29 of every 30 dates as never-fetched: `coverage --from 2026-01-01 --to 2026-09-04` (no --resource, the documented default = all) yields roughly 240 fabricated holes per monthly resource against ~8 real rows, and summary.dates_never_fetched — the contract's summary field — reports those fabrications as mirror gaps. --gaps-only in the default scope becomes almost entirely noise. The Long help at coverage.go:104-106 discloses the cadence but the counts still ship it; disclosure does not make dates_never_fetched correct. Related aggravator: verify.go:120-129 documents that allocation is sometimes mirrored under MUFAP's M-YYYY key ("7-2026"); the lexical date filter in store.LoadMUFAPCoverage (internal/store/mufap_schema.go:196-204) excludes such a row from an ISO --from/--to window entirely, so that month reports never-fetched on every one of its days. Fix: walk month-ends for monthly/allocation, or exclude them from the default walk scope unless named by --resource.

[MINOR] "never-fetched" silently absorbs failed attempts, which the Short description at coverage.go:93 ("which were never attempted") and the Long help at coverage.go:99 ("no ledger row exists for that calendar date at all") present as never-attempted. store.SaveMUFAPDate is only reached on the success path (backfill.go:451, 564, 744); every fetch or parse failure takes backfillAddErr + continue and writes no coverage row. So a date fetched five times, failing every time, is reported identically to one nobody ever asked for — status never-fetched at coverage.go:231. The ledger schema cannot currently support the distinction (internal/store/mufap_schema.go:69-77 has no outcome column), so the defect here is the overstated claim: the wording should read "no ledger row: never attempted, or every attempt failed".
