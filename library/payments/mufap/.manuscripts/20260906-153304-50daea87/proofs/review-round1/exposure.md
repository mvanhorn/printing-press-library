# Review findings for internal/cli/exposure.go

[BLOCKER] Context expiry silently drops un-dequeued jobs, producing genuine zero rows — the exact failure mode the contract forbids. $HOME/printing-press/.runstate/personal-74f0f171/runs/20260906-153304-50daea87/working/mufap-pp-cli/internal/cli/exposure.go:423-432: the feeder goroutine does `case <-ctx.Done(): return` and then `close(queue)`, so once the command context expires every job still in the `jobs` slice is discarded. Those fund-months are never fetched, never error-tagged, and never recorded — they are not in FailedFunds, not in AbsentFunds, not in FundsAttempted, and not in FetchFailures. Meanwhile lines 441-447 pre-create a *exposureMonthRow for EVERY month in `months`, and lines 498-505 append all of them unconditionally, so a month whose jobs were all dropped is emitted as {"stocks_pkr_million":0,"net_assets_pkr_million":0,"equity_share":0,"fund_count":0,"absent_funds":0,"failed_funds":0,"funds_attempted":0}. Nothing returns an error and RunE exits 0. This is not a corner case: boundCtx (line 267) applies root --timeout, which defaults to 60s (root.go:298), and the command's own advertised Example on line 258 is `--from 2024-01 --to 2026-07 --concurrency 6` — 31 months x ~400 funds is roughly 12,000 POSTs, which cannot finish in 60s, so the shipped example reliably prints fabricated zero months for the industry equity series this command exists to produce. The sibling fan-out in verify.go:192-194 handles this correctly (`if ctx.Err() != nil { return ..., ctx.Err() }`). Fix: after the drain loop at line 437-439, check ctx.Err() and either return it or record each un-dispatched job as a failure (e.g. stage "budget", error "run budget expired before this fund-month was attempted") so it lands in fetch_failures and FailedFunds instead of vanishing.

[MAJOR] AMC fund-list failures are attributed to no month, so per-month failed_funds reads 0 while an entire AMC's book is missing from the sums. exposure.go:169-173 builds the Stage "funds" failure with only Stage/AMC/Error — the Month field is left "". The fold loop at lines 478-486 only touches Stage "fund-code" entries, and byMonth[""] is nil anyway, so nothing increments FailedFunds or FundsAttempted for the affected months. Simultaneously line 445 stamps every month row with `AMCCount: len(amcs)`, the count of AMCs *selected*, not the count that actually listed funds. Net effect on a run where 5 of 27 AMCs 500 on GetFundNameByAMC: each month row reads amc_count:27, failed_funds:0, fund_count:<short>, while stocks_pkr_million is missing five AMCs' worth of equity. A consumer using failed_funds==0 as the "this month is clean" gate — the natural reading given the contract promises failures are surfaced per month — is silently wrong. The contract requires universe width to be visible per month; here the per-month width is overstated and the loss is only discoverable by cross-referencing the flat fetch_failures array. Fix: fan the funds-stage failures across every month in the range (or add explicit amcs_failed / amcs_resolved fields to exposureMonthRow) so the per-month denominator reflects what was actually reachable.

[MINOR] The live-fetch path books a fund at zero when its Total or StocksOREquities field is missing, contradicting the guard the same file documents for the cache path. exposure.go:411-413 does `res.Stocks, _ = mufapAllocNumber(row, exposureStocksField)` and `res.Total, _ = mufapAllocNumber(row, exposureTotalField)`, discarding the ok flag; the row then falls through to lines 467-473 and is counted in FundCount with 0 contributed to both sums. exposureLoadCache at lines 220-224 explicitly refuses to do this, with the comment "trusting it would silently book the fund at zero" — the live path (the command's primary path, per the contract's LIVE FAN-OUT framing) does not apply the same rule. The cache-hit path at lines 377-378 has the same discard, protected only by the Total presence check at load time, so a cached row with a Total but a null StocksOREquities is likewise counted as a reporting fund holding zero equity. Fix: honour the ok flag on exposureTotalField and record a !ok row as a failure (or a distinct "unparseable" bucket) rather than as a fund_count member.

[MINOR] exposure.go:343 tells the user to run the wrong backfill subcommand. The missing-mirror guard prints "run: mufap-pp-cli backfill daily --from <date> --to <date>", but this command reads the resource keyed "allocation" (exposureAllocResource, line 25; exposureLoadCache line 206). `backfill daily` mirrors the daily fund panel and never writes an allocation row — the populating command is `backfill allocation` (backfill.go:583, which stores under `const resource = "allocation"` at backfill.go:627). A user who follows the printed advice runs a long backfill and comes back to a cache that still misses on every fund. The string appears to be copied from verify.go:350. Fix: print `backfill allocation --from <YYYY-MM> --to <YYYY-MM>`, matching the example already in the command's own Long text region.

[MINOR] A required-input usage error is raised after the network fan-out has already run, violating the RunE ordering rule. exposure.go:357-361 calls mufap.MonthKey(m) inside the month loop and returns usageErr(keyErr) on failure — but that loop sits after mufapFetchAMCs (line 325) and exposureListUniverse's full per-AMC fund-list fan-out (line 335). exposureParseMonth (line 109) accepts any year time.Parse will take, while mufap.MonthKey rejects years outside 1990-2200 (parse.go), so `--from 1899-01` passes validation at line 277, issues ~28 live POSTs, and only then exits 2 with a usage error. The months slice is fully known at line 300-303; the MonthKey conversion (and its error) can be hoisted there, before flags.newClient() at line 320, at no cost.
