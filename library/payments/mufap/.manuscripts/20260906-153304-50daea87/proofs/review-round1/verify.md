# Review findings for internal/cli/verify.go

[MAJOR] verify.go:235 + 397-400 — the live path throws away every completed check when the run hits the --timeout deadline. verifyAllocationLiveRows deliberately returns the partial `rows` slice alongside ctx.Err() (line 235: `return rows, len(amcs), absent, fetchErrs, ctx.Err()`), signalling that partial work is meant to survive, but the caller does `rows, amcCount, absent, fetchErrs, err = verifyAllocationLiveRows(...)` and then `if err != nil { return classifyAPIError(...) }` (399), which discards the assigned rows and exits 5 with no report at all. This is not a rare path: the file's own comment at 335-337 says the full industry is "~500 POSTs", the default --concurrency is 4, and the root default --timeout is 60s (root.go:298) with --rate-limit auto-pacing on top — so the command's own headline Example (`verify allocation --month 7-2026`, line 250/291) is the invocation most likely to fetch 300+ funds successfully and then print nothing. Neither Long nor Example mentions raising --timeout, unlike `backfill allocation`, whose Long explicitly says "Expect it to be slow and to need a raised --timeout" (backfill.go:588-589). Either surface the partial run (report rows with a truncated/deadline flag, as the helper's return signature already anticipates) or tell the user to raise --timeout in the help.

[MINOR] verify.go:352 — the missing-mirror branch emits a different JSON type than every other machine-output path of the same command. Success emits the verifyAllocationReport object `{"summary":{...},"funds":[...]}` (440-443), but when --db points at a path that does not exist this returns `printJSONFiltered(cmd.OutOrStdout(), make([]verifyAllocationRow, 0), flags)` — a bare `[]`. An agent or `jq '.summary.failed'` consumer gets a type error rather than a zeroed report. rates.go:110 uses the same empty-slice idiom legitimately because its success payload is also a slice; here the shapes diverge. Emit an empty verifyAllocationReport (summary with source "local" and zero counts) instead.

[MINOR] verify.go:136-140 — the local (--db) reader silently drops mirror rows whose payload will not JSON-decode (`continue` with no counter), and nothing in verifyAllocationSummary records that it happened. The live path is careful about exactly this (FetchErrors at 209-211, Absent at 213-217, both surfaced in the summary at 418-419 and in the human line at 450-452), so a corrupted mirror understates `funds` — the universe width the summary is supposed to make visible — with no signal at all. Add a decode-error counter to the summary and to the human output, mirroring FetchErrors.

[MINOR] verify.go:368-370 vs 483 — the --max-amcs help text promises "Check only the first N AMCs alphabetically", and the live path honours it (sort.Slice by AMC name at 155, then truncate at 156-158). The --db path does not: it caps on a `seenAMC` set filled in mirror row order, which store.LoadMUFAPObs returns as `ORDER BY date, row_key` and backfill.go:733 sets row_key to the integer fund code rendered as text. So `verify allocation --month 2026-07 --max-amcs 1 --db ...` checks whichever AMC owns the lexically-smallest fund code, not the alphabetically-first AMC, and the same flag silently selects a different AMC live vs. local. This also applies under the dogfood cap (334-338), which forces maxAMCs=1.

[MINOR] verify.go:434-437 and 469 — WorstFund is only assigned inside `if math.Abs(r.Deviation) > math.Abs(summary.WorstDeviation)`, a strict comparison against a zero-initialised WorstDeviation, so when every populated fund nets to exactly 100.0 (entirely plausible for a fund reporting 100.00 in a single asset-class column and 0 elsewhere, which sums to exactly 100.0 in float64) WorstFund stays "". Line 469 then prints `worst deviation +0.0000 pp ()` with empty parentheses, and the JSON drops worst_fund via omitempty while still reporting worst_deviation. Seed WorstFund from the first populated row, or suppress the parenthetical when WorstFund is empty.
