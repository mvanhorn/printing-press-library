# Review findings for internal/cli/rates.go

[MAJOR] rates.go:121-124 — missing-mirror guard is incomplete: no "no such table" fallback on store.LoadMUFAPObs. The os.Stat guard at rates.go:107 only covers a DB file that does not exist. The mirror file is SHARED with the platform's own tables and is created by the teach/learn loop (teach.go:144 resolves the same defaultDBPath("mufap-pp-cli") as rates.go:105), so data.db routinely exists with no mufap_obs table at all. A read-only handle (store.OpenReadOnlyContext, mode=ro&immutable=1) cannot create it, so LoadMUFAPObs returns "mufap load: query: no such table: mufap_obs" and rates.go:123 returns it bare — the user gets a raw SQLite string at exit 1 instead of the empty-mirror path (empty JSON array / 'run: backfill daily' guidance) the contract requires. Every other local-store reader in this package guards exactly this: dispersion.go:150, universe.go:195, coverage.go:197, export.go:178, and panel.go:171-185 (which pre-checks sqlite_master and carries the comment "a `teach` run creates it ... LoadMUFAPObs would surface that as a raw 'no such table: mufap_obs'"). rates.go is the only one that does not. Fix: mirror the dispersion.go:149-153 shape — on strings.Contains(err.Error(), "no such table") fall through to the same empty-mirror return used at rates.go:107-113.

[MAJOR] rates.go:47-48 (Long) and rates.go:176-180 (comment) promise hole-visibility the code does not deliver for the most common hole. Both claim that a date MUFAP published nothing on "stays in the JSON with fund_count 0 so the hole remains visible there". But the date list is built only from rows returned by LoadMUFAPObs (rates.go:129-144), and a fetched-and-empty date is stored with ZERO obs rows: backfill.go:436-439 ("Fetched-and-empty is a fact worth storing: it is what separates a holiday from a date nobody ever tried") saves the date with an empty row slice, so SaveMUFAPDate writes only a mufap_coverage row (row_count 0) and no mufap_obs rows — the package even tracks these as sum.ZeroRowDates (backfill.go:60,459). Such a date therefore never enters `dates`/`points` and is SILENTLY MISSING from the JSON — precisely the failure mode the contract's "rather than silently missing rows" clause exists to prevent. Only the narrower case (a date that has stored rows, none of them annualized money-market) actually produces fund_count 0. Consequence: an agent reading --help concludes a date absent from the series was never mirrored and is told to re-run 'backfill daily' (rates.go:195), when the date was already fetched and is genuinely empty. Either cross-join the coverage ledger (store.LoadMUFAPCoverage) so zero-row dates get emitted as fund_count 0, or correct both texts to say only stored-but-non-money-market dates are surfaced.

[MINOR] rates.go:123 — `return err` returns the store error unwrapped, with no command context. Every sibling wraps (dispersion.go:154 `fmt.Errorf("dispersion: %w", err)`; panel.go:178 wraps its schema read). A user piping stderr sees "mufap load: query: ..." with nothing identifying which command failed.

[MINOR] rates.go:138-142 with rates.go:156-158 — a date whose stored payloads all fail to json.Unmarshal emits a point with fund_count 0, which in the JSON is byte-identical to a date that genuinely had no money-market fund. The distinguishing fact (the `malformed` count) goes only to stderr as an un-dated aggregate and never into the emitted []mufap.RatePoint, so a machine consumer reading stdout cannot tell a mirror-format failure from a thin date. This is the same 'failed reads must not read as zeros in an aggregate' hazard the file's own comment at rates.go:134-137 sets out to avoid; it is avoided for fund_count but not for the JSON consumer.

[MINOR] rates.go:185-191 — no thin-cross-section warning. A date with a single reporting fund prints MEDIAN = P10 = P90 = that one fund's yield, which reads as a zero-dispersion market-wide policy-rate proxy. The FUNDS column and fund_count do surface the width (so the contract's item 7 is technically met), but the sibling command sets a higher bar for the identical statistic: dispersion.go:37-40 defines `dispersionMinFunds = 3` and dispersion.go:181,187-197 emits an explicit stderr/JSON-event warning below it, with the reasoning that percentiles over fewer than three funds are "the distance between two funds". rates.go derives p10/p90 from the same Percentile helper and issues no such warning.

[MINOR] rates.go:193-197 vs rates.go:202-204 — when every derived point is thin (points non-empty but all FundCount 0), the len(rows)==0 branch returns at rates.go:196, making the `thin` disclosure at rates.go:202-204 unreachable. The user is told "no annualized money-market yields ... run: backfill daily" even though the mirror IS populated for those dates (just with no annualized money-market rows), so the suggested remedy will not change the outcome, and the pointer to --json listing them with fund_count 0 is never printed in the one case where it matters most.
