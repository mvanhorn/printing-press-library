# Review findings for internal/cli/backfill.go

[BLOCKER] backfill.go:744 — `backfill allocation` commits the month snapshot unconditionally, so failed fetches are recorded as zeros. Inside the month loop, a failed `mufapFetchFunds` (line 702-705) or a failed `mufapFetchAllocation` (line 717-720) only appends to `sum.Errors` and `continue`s; nothing tracks that the fan-out was incomplete. Control then falls to line 744 `store.SaveMUFAPDate(ctx, s, resource, monthEnd, rows, time.Now())` with a `rows` slice that may be empty *solely because every request failed*. That writes a `mufap_coverage` row with `row_count = 0` (store/mufap_schema.go:130-135), line 750-751 pushes the month onto `sum.ZeroRowDates`, and backfillEmit renders it under the human label "published nothing" (backfill.go:112) — i.e. a total-outage month is reported to the caller as MUFAP legitimately having no data. It is then sticky: line 660 `if fetched[monthEnd] && !opts.force { sum.DatesSkipped++; continue }` skips it on every subsequent run. Compare `backfill daily` (line 390-392) and `backfill monthly` (line 557-559), which both `continue` before saving when the fetch fails — allocation is the one path that violates the contract's "failed fetches never counted as zeros in an aggregate".

Same line, second trigger: the two `if ctx.Err() != nil { break }` guards at lines 697-699 and 714-716 break out of the AMC/fund loops on timeout and fall straight through to the line-744 save, so a month that ran out of `--timeout` halfway through the fan-out is committed as a complete snapshot. The very next iteration then records "run budget expired at %s; re-run to resume from here" (line ~683), but the resume it promises will skip that month because the ledger now says it was fetched. Fix: track a fan-out-failure/incomplete flag (any error recorded for this month, or ctx cancellation) and skip the SaveMUFAPDate + zero-row accounting for that month, or write coverage only when the fan-out completed.

[MAJOR] backfill.go:455 (with 384) — in `backfill daily`, a ragged carry poisons a later date in the same requested range. Line 455 `fetched[gd] = true` marks every committed validity date as fetched, including a carried date `gd != date`. If `gd` is still ahead in the `dates` slice being iterated, line 384 `if fetched[date] && !opts.force { sum.DatesSkipped++; continue }` then skips that date's own explicit fetch. Concretely: `backfill daily --from 2026-09-01 --to 2026-09-05`; the 09-01 response carries three stray rows whose Validity Date is 2026-09-03. Those 3 rows are stored as the 2026-09-03 snapshot, `fetched["2026-09-03"]=true`, and when the loop reaches 09-03 it is counted in `dates_skipped` and never fetched — so a 3-row partial view permanently stands in for the ~300-row panel and the coverage ledger reports the date as done. This inverts the command's own documented rule (Long text, line ~309: "a stray row is a partial view and must not replace a complete snapshot") and the guard at line 445 that enforces it for pre-existing dates. Fix: do not seed `fetched[gd]` for a carried date that is still pending in `dates`, or defer carried-date writes until the range's own pass over that date is done.

[MAJOR] backfill.go:444-451 — `--force` disables the ragged-carry guard for dates outside the requested range, causing destructive out-of-range overwrite. `opts.force` is a whole-run flag meaning "re-fetch the dates I asked for", but line 445 `if fetched[gd] && !opts.force` uses it to also authorize overwriting a carried date the caller never named. `store.SaveMUFAPDate` replaces the snapshot wholesale — `DELETE FROM mufap_obs WHERE resource = ? AND date = ?` (store/mufap_schema.go:115) — before inserting. So `backfill daily --from 2026-09-03 --to 2026-09-03 --force` on a response that happens to carry 3 stray rows dated 2026-08-14 deletes the complete, previously-mirrored 2026-08-14 snapshot and leaves 3 rows plus a `row_count = 3` coverage row in its place. Nothing in the run reports the loss beyond the stderr line at 449. Fix: gate the guard on membership in the requested range rather than on `opts.force` — force should only override the skip for dates in `[from, to]`.

[MAJOR] backfill.go:284 — the `backfill` parent swallows an unknown subcommand as exit 0. The parent has subcommands, so cobra's `legacyArgs` allows arbitrary args on a non-root command and dispatches `backfill dail --from=... --to=...` to the parent's RunE with `args == ["dail"]`; line 284 `return cmd.Help()` ignores `args` entirely, prints help on stdout and exits 0. A caller (especially the MCP/agent path, which gets non-JSON on stdout and a success code) is told the write succeeded when nothing was written. Every other parent group in this package routes through `parentNoSubcommandRunE` (helpers.go:252-278), which emits `{"error":"unknown subcommand",...}` under `--json` and returns `usageErr` (exit 2) — see verify.go:256 and vps.go. Fix: `return parentNoSubcommandRunE(flags)(cmd, args)` after the dry-run branch, which still satisfies "the parent just shows help" for the bare `backfill` case.

[MINOR] backfill.go:486 and backfill.go:599 — declared `pp:happy-args` do not match the contract. The contract specifies `--from=2026-09-03;--to=2026-09-03` for the backfill annotations; `backfill monthly` and `backfill allocation` declare `--from=2026-07-31;--to=2026-07-31` instead (the parent at line 276 and `daily` at line 316 do match). The substituted value is domain-sensible — 2026-09-03 parsed as a month yields month-end 2026-09-30, a future month-end that would return an empty panel today — but it is still a silent deviation from the stated contract, so either the contract or the annotation should be reconciled explicitly rather than left divergent.

[MINOR] backfill.go:273-277 — the `backfill` parent declares `mcp:local-write: "true"` and `pp:happy-args` but omits `pp:parent-group: "true"`, so tooling that enumerates annotations sees a help-only group advertised as a runnable local-write command with happy-args. The package convention for help-only groups is to carry that marker: verify.go:251 (`"pp:parent-group": "true"`) and vps.go:14. Add `"pp:parent-group": "true"` to the parent's annotation map.
