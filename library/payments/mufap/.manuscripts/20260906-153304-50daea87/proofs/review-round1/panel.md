# Review findings for internal/cli/panel.go

[BLOCKER] universe_width undercounts the universe by ~12.6% on the default tab, which is the one number this command exists to report honestly. panel.go:207-218 derives `fund := payload["Fund Name"]` and then counts the universe with `funds[fund] = true` (line 218) -> `view.UniverseWidth = len(funds)` (line 249). The run's own measured discovery note (discovery/endpoint-contract.md section G, "ROW KEY -- measured 6 Sep") states that on 2026-09-04, tab=returns, 388 rows collapse to only 339 distinct Fund Names: 49 collisions, 12.6%, because VPS pension funds legitimately repeat their name ("ABL Pension Fund" is three genuinely different sub-fund series -- VPS-Money Market, VPS-Debt, VPS-Equity). The note's verdict on exactly this key choice: "Keying on `Fund Name` alone would drop 49 of 388 rows per date -- 12.6% ... with no error raised anywhere." The store already carries a per-date-unique key: MUFAPObs.Key, PRIMARY KEY (resource, date, row_key). The sibling command uses it -- universe.go:242-246 counts `keys[o.Key]` per date and will report fund_count 388 for the same date and range that panel reports universe_width 339, so the two commands in this CLI disagree by ~13% on the same question. Fix: count the universe on `o.Key` (or on a Sector|Category|Fund Name composite), not on the display name; keep the display name only for the row's `fund` field and for --fund matching.

[MAJOR] The promoted `fund` column reads a header that does not exist on 4 of the 5 selectable tabs. panel.go:207 does `fund := payload["Fund Name"]` with a fallback to `o.Key`. discovery/endpoint-contract.md section H measured the headers per tab: returns -> "Fund Name"; nav, pricing, payout, ter -> "Fund", with the explicit instruction "Resolve by probing which header is present rather than by tab number." The sibling writer already does this -- backfill.go `backfillRowKey` probes []string{"Fund Name", "Fund"} and documents the same hazard. Consequences on --tab nav/pricing/payout/ter (a shape this command advertises itself, Example line 66 `--tab nav`): (a) `fund` silently falls back to the store's row key, so its value depends on the backfill's key format rather than on the data -- duplicate rows surface as "<name> #2" (backfillUniqueKey) and a row with neither header surfaces as "row-7"; (b) the switch at panel.go:240 skips "Fund Name"/"Category"/"Sector" but not "Fund", so those rows carry both `fund` and a redundant verbatim `Fund` key; (c) the --fund flag help at panel.go:342 promises "rows whose Fund Name contains this text" on tabs that have no Fund Name column. Fix: probe "Fund Name" then "Fund" at line 207 and add "Fund" to the skip list at line 240.

[MAJOR] universe_width and the summary prose are emitted unqualified for --tab pricing and --tab ter, which are not date-filtered panels. panel.go:87-96 accepts all five MUFAPDailyTabNames, then line 249 sets UniverseWidth and lines 329-330 print "%d distinct funds reported across %d dates in %s" identically for every tab. discovery/endpoint-contract.md section H measured that pricing and ter return 551 rows for an explicit date while returns returns 388, and states directly: "those two tabs are current reference data and are NOT date-filtered the same way. Do not read their row counts as a universe width for that date." So for two of five tabs the command's headline field means something other than what its own doc comment (panel.go:23-28) and Long text (lines 58-60) claim it means, and a caller comparing universe_width across --tab returns and --tab ter reads a 40% jump as an industry expansion. Fix: either suppress universe_width for pricing/ter, or carry a per-tab caveat field (e.g. universe_width_reliable=false) and say so in the human summary.

[MINOR] The date semantics for --tab payout are misdescribed. panel.go:337-338 document --from/--to as "Earliest/Latest validity date", and the comment at lines 102-106 justifies accepting MUFAP's display form "because that is what the Validity Date column shows". discovery/endpoint-contract.md section H measured that tab=payout has NO Validity Date column at all -- its date is "Payout Date" -- so on that tab the stored `date` this command filters on and emits is a payout date, not a validity date. The human column-preference list at panel.go:286 likewise names "Validity Date" but never "Payout Date", so payout rows fall through to the generic sorted-first-6 fallback. Fix: qualify the flag help and Long text for the payout tab, and add "Payout Date" to the preferred column list at line 286.

[MINOR] Rows whose payload fails to decode are dropped without being counted anywhere, so a partially corrupt mirror silently shrinks the very aggregate the command exists to report. panel.go:202-206 does `if err := json.Unmarshal(...); err != nil { continue }` before the row contributes to `dates`, `funds` or `Matched`, and panelView (lines 29-41) has no field for the skipped count. The result is indistinguishable from a genuinely narrower universe -- the same failure mode the contract guards against with "failed fetches never counted as zeros in an aggregate", and the same distinction the store itself is careful to preserve elsewhere (MUFAPCoverage's doc comment on RowCount 0). Fix: add a `skipped` (or `unreadable_rows`) counter to panelView, increment it at line 205, and mention it in the human summary when non-zero.
