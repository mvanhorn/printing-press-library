## Customer model

### Mike — recovering personal conversation context

**Today (without this CLI):** Mike has an established local Signal/Telegram collection workflow, but a Google Voice question still sends him to Voice's conversation list and message history. Recovering an earlier exchange requires remembering the thread and scrolling until the relevant messages appear.

**Weekly ritual:** Check recent personal communication and recover earlier context for a concrete question, while leaving relationship interpretation to separate skills.

**Frustration:** A matching phrase alone does not establish who participated, which exchange it belongs to, or what was said immediately around it.

### Chief-of-staff agent — answering from observed evidence

**Today (without this CLI):** The agent can query the existing messaging archive but cannot treat Google Voice history as another verified, account-scoped local source. Even after collection exists, a zero-result query is ambiguous unless it can inspect what was actually collected.

**Weekly ritual:** Retrieve evidence for a specific question, check freshness and collection boundaries, then pass accurately bounded observations to the appropriate reasoning skill.

**Frustration:** An empty result can mean no matching observed message, an unvisited thread, unfinished older pagination, or a failed recent refresh; those states must remain distinguishable.

### Mac Studio collector operator — maintaining repeatable imports

**Today (without this CLI):** The operator already maintains bounded, hourly personal-message imports for other services. Adding Google Voice requires checking committed pages, saved cursors and duplicate handling rather than relying on the date of the newest message as a success signal.

**Weekly ritual:** Inspect collection progress, resume unfinished work, and establish which records actually arrived during recent runs without confusing old backfill with recent communication.

**Frustration:** A successful process exit or a recent message timestamp does not identify all unfinished work or explain what a backfill added to the archive.

Every surviving command uses `// pp:data-source local`, rejects `--data-source live` with a clear no-live-equivalent error, and makes no remote service call. Each calls `hintIfUnsynced` for the message resource, then `hintIfStale` when appropriate; coverage also checks the relevant run/inventory resources. These hints go to stderr and respect `--max-age 0`. Account identity scopes every query, and deterministic ordering includes a stable source ID tie-breaker. All examples above invoke hand-written novel commands rather than inventing flags for framework commands.

Local query plans use parameterized SQL. Prefer one joined/aggregated query; when a second lookup is necessary, drain the first result into structs, check `rows.Err()`, close `rows`, and only then expand IDs or query children. No implementation may query a second result set while a parent `*sql.Rows` remains open on the single SQLite connection. The arrivals feature's first-seen fields are written through the existing page `*sql.Tx` together with imported records and the continuation checkpoint; it must not call pooled `store.Upsert` or `store.UpsertBatch` inside that open transaction, and any write error fails the command.

**1 — Compound message evidence.** **Weekly use:** Mike or the agent uses it during the brief's recurring recent-communication/context ritual. **Wrapper vs leverage:** It is not a renamed `/api2thread/get`; predicates join several local entities and can search across already mirrored threads. **Transcendence proof:** Parameterized SQLite joins combine independently observed participant, message and attachment facts into one bounded result. **Sibling kill:** `history media` is killed because attachment presence is one query condition rather than a second tool. **Buildability:** `hand-code`; a single composed SQL query plus bounded output/Cobra wiring fits the roughly 50–150-line feature shape using shared store helpers. **Long-description validity:** The redirect names the surviving `history context` exactly. **Edges:** Match explicit source identifiers or conservatively normalized exact numbers, never display-name guesses; use `[after, before)` source-message time; an empty result means no matching local record, and attachment presence means metadata rather than downloaded bytes.

**2 — Message-anchored context packet.** **Weekly use:** The agent uses it when grounding a concrete answer in recovered messages during the repeated context-recovery ritual. **Wrapper vs leverage:** It takes a message anchor, not an API thread page, and selects adjacent locally observed records with a fixed evidence budget. **Transcendence proof:** Local ordering and agent-shaped provenance turn a match into inspectable surrounding evidence without an LLM. **Sibling kill:** `history digest` is killed because interpretation belongs downstream; the useful mechanical extraction survives here. **Buildability:** `hand-code`; anchor lookup followed by drained/closed-row neighbor queries and fixed packet serialization fits the roughly 50–150-line feature shape with shared metadata helpers. **Long-description validity:** The redirect names the surviving `history query` exactly. **Edges:** Reject a missing/wrong-account anchor; cap neighbor counts; stay within the original thread; distinguish a requested window clipped by output limits from known pending pagination and from unknown coverage, and never assert that locally adjacent rows are all messages ever sent between those times.

**3 — Question-scoped coverage evidence.** **Weekly use:** The agent checks it before relying on a no-result query, and the operator checks it during the explicit import-maintenance ritual. **Wrapper vs leverage:** No one RPC or one sync exit code joins global folder discovery, individual thread refresh/history states and a proposed lookup's scope. **Transcendence proof:** Local checkpoint/run/inventory joins show the provenance of an absence without converting observed timestamp bounds into a completeness claim. **Sibling kill:** `mirror watch` is killed because a one-shot evidence query supplies the needed inspectable state without a resident process or installer. **Buildability:** `hand-code`; bounded SQL aggregates and state projection fit roughly 50–150 lines plus shared observation fields, with unknown states preserved when observation data is absent. **Long-description validity:** The redirect names the surviving `history activity` exactly. **Edges:** Include account-wide folder-inventory state even for an unmatched participant, because undiscovered threads cannot be ruled out; retain partial-run failures and pending cursors; distinguish successful refresh time from message time; report per-observation exhaustion without a global continuous-history or atomic-snapshot claim.

**4 — Newly mirrored records.** **Weekly use:** The operator and agent use it to review what collection added since their last reviewed run, including historical backfill. **Wrapper vs leverage:** First-observed collection time is local state and is not an API message-list filter. **Transcendence proof:** Joining immutable ingestion provenance to source timestamps distinguishes archive growth from communication recency and makes repeated syncs verifiably quiet for already seen IDs. **Sibling kill:** `history revisions` is killed because preserving every observed mutation adds a versioning subsystem without an established weekly question. **Buildability:** `hand-code`; one immutable first-seen stamp in the page transaction, a parameterized seek query and an opaque bounded continuation fit the small command shape, while source-body version storage is excluded. **Long-description validity:** The redirects name the surviving `history query` and `history activity` exactly. **Edges:** Require a terminal, same-account run watermark; a resumed collection invocation gets a new run ID; paginate over immutable first-seen sequence/ID with a fixed upper watermark; repeated observation of an existing source ID yields no arrival, and metadata updates are outside this command's contract.

**5 — Observed conversation activity.** **Weekly use:** Mike and the agent use it for the brief's recurring check of recent personal communication before a separate skill interprets those observations. **Wrapper vs leverage:** No thread-list/read endpoint yields windowed inbound/outbound aggregates together with exact participants and collection evidence. **Transcendence proof:** Cross-entity SQLite aggregation provides deterministic observed facts with group threads kept distinct and empty windows qualified by coverage. **Sibling kill:** `relationships overdue` is killed because it converts observations into unapproved relationship policy; only counts and source timestamps survive. **Buildability:** `hand-code`; grouped conditional SQL aggregates plus participant/coverage projection fit roughly 50–150 lines with existing store helpers, without contact resolution or a scoring engine. **Long-description validity:** The redirect names the surviving `history query` exactly. **Edges:** Count only verified/decoded text and MMS events using source-message time; retain or explicitly report unknown directions/types rather than guessing them; keep group conversations at thread scope; zero observed counts do not establish no contact, and there is no cross-service identity merge, reply obligation or relationship score.
