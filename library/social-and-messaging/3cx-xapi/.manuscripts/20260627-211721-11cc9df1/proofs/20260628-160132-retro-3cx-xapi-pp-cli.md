## Findings

### 1. doctor reports "Auth: not configured" for OAuth2 client-credentials until a token is minted (Bug)
- **What happened:** With valid `TCX_CLIENT_ID`/`TCX_CLIENT_SECRET` set and live API calls succeeding, `doctor` reported `Auth: FAIL not configured`.
- **Scorer correct?** N/A (not a scorer finding) — generated `doctor` template logic.
- **Root cause:** `internal/cli/doctor.go` decides auth via `cfg.AuthHeader() == ""`. For the `client_credentials` flow the Bearer token is minted lazily on the first API call, so `AuthHeader()` is empty at doctor time even when credentials are fully configured.
- **Cross-API check:** Recurs for every printed CLI whose auth is OAuth2 `client_credentials` — a first-class auth mode the generator supports. Not OData-specific.
- **Frequency:** every client_credentials CLI.
- **Fallback if the Printing Press doesn't fix it:** Agent hand-patches doctor each time (this run did). Easy to miss; ships a misleading `doctor` FAIL.
- **Worth a fix?** Yes — misleading health output for a whole auth class.
- **Durable fix:** In the doctor template, treat presence of client id + secret (env or config) as configured auth for the `client_credentials` flow, in addition to a minted header.
- **Test:** positive — set only client id+secret (no minted token), `doctor` reports `configured`. negative — no creds at all → still `not configured`.
- **Evidence:** `doctor` FAIL "not configured" with `Env Vars OK 2/2` while a live `users list` returned data.
- **Related prior retros:** None (first 3cx retro; no cross-API match available offline).

### 2. Non-JSON response endpoints (CSV/file export/download) error instead of emitting the body (Template gap)
- **What happened:** ~42 generated `export`/`download` endpoint commands fail (exit 5 "API returned a non-JSON response; expected JSON"). Confirmed `users export-extensions` returns valid `text/csv` (HTTP 200).
- **Scorer correct?** Partially — dogfood correctly flags the non-zero exit; the underlying cause is a generator gap.
- **Root cause:** Generated endpoint commands always call the JSON-guarded read path. The read path **already has the lever** — `resolveReadWithStrategyResponsePathAndJSONGuard(..., guardLiveJSON=false, ...)` in `internal/cli/data_source.go` — but the generator never emits the `guardLiveJSON=false` call (nor a raw-body output path) for endpoints whose spec response content-type is non-JSON.
- **Cross-API check:** Any API with file/CSV/binary download or export endpoints. The existing `guardLiveJSON bool` parameter is direct architectural evidence the maintainers anticipated non-JSON responses.
- **Frequency:** every API with non-JSON-response endpoints (common: report exports, CSV downloads, file fetches).
- **Fallback:** Agent edits per-command (regen-fragile across dozens of files) or documents as a gap (this run did the latter).
- **Durable fix:** Generator detects a non-JSON response content-type in the spec for an endpoint → emits the `guardLiveJSON=false` read call and writes the raw response body to stdout (optionally `--output <file>`), instead of the JSON pipeline.
- **Test:** positive — an endpoint declared `text/csv` emits the raw CSV at exit 0. negative — a normal JSON endpoint is unchanged (still guarded).
- **Evidence:** `users export-extensions` → exit 5; raw curl shows `CT=text/csv; charset=UTF-8` with valid CSV body.
- **Related prior retros:** None offline.

### 3. Generator references a missing workflow template `workflows/comm_health.go.tmpl` (Bug)
- **What happened:** `generate` printed `warning: skipping workflow template workflows/comm_health.go.tmpl: ... file does not exist` on both generation passes.
- **Scorer correct?** N/A.
- **Root cause:** A generator code path (likely category/workflow-driven for `social-and-messaging`) references an embedded template that isn't present in the template set.
- **Cross-API check:** Any CLI whose category/workflow selection reaches the `comm_health` workflow.
- **Frequency:** category-scoped (subclass), but a concrete defect regardless of frequency.
- **Fallback:** None needed (workflow silently skipped) — but it's a dangling reference that should not ship.
- **Durable fix:** Add the missing `comm_health.go.tmpl` to the embedded templates, or remove the reference if the workflow is deprecated.
- **Test:** generate a `social-and-messaging` CLI → no missing-template warning.
- **Evidence:** generate-log warning, both passes.
- **Related prior retros:** None offline.

### 4. OData (Microsoft.OpenApi.OData) spec subclass: Number-keyed entities drop on sync; function-style paths break the verify mock harness (Assumption mismatch — subclass:odata)
- **What happened:** (a) `did-numbers` (and other `Number`-keyed entities) synced 0 rows with `no extractable ID field` until `number` was added to the ID fallback list. (b) Polish observed verify `data_pipeline: "sync crashed"` because the spec-derived verify mock harness can't route OData function-style paths (e.g. `/ActivityLog/Pbx.GetFilter()`), so all resources error under the no-credential mock.
- **Scorer correct?** (b) is a scorer limitation — verify's data-pipeline marks "sync crashed" for OData function paths even though sync is correct (dogfood pipeline GOOD, live sync 172 records, scorecard Sync Correctness 10/10).
- **Root cause:** (a) `genericIDFieldFallbacks` (in `internal/store/store.go` and `internal/cli/sync.go`) lacks `number`; PascalCase `Id` matched via `LookupFieldValue`'s Pascal fallback but `Number` had no entry. (b) the verify mock server doesn't serve OData function-call path segments.
- **Cross-API check:** OData-derived specs (detectable via `x-ms-generated-by: Microsoft.OpenApi.OData` or an OData `$metadata` document). Catalog OData coverage appears thin → subclass.
- **Frequency:** subclass:odata. *(Part (a) — adding `number` — is broadly safe and helps ANY Number-keyed resource, not just OData.)*
- **Fallback:** (a) silent zero-row sync → empty offline mirror → flagship local commands return nothing. High-harm, hard to notice (no error). (b) misleading verify FAIL.
- **Durable fix:** (a) add `"number"` to `genericIDFieldFallbacks` (ordered after the id-family/identifier names — safe). (b) teach the verify mock harness to route OData function-call paths, or exclude OData function endpoints from the data-pipeline sync probe.
- **Test:** (a) sync a Number-keyed resource → rows stored. (b) verify on an OData spec → data-pipeline not falsely "crashed".
- **Evidence:** `did-numbers` 35 items → 0 stored "no extractable ID field"; fixed after adding `number`. Polish data_pipeline note.
- **Related prior retros:** None offline.

## Anti-patterns
- Hardcoding the customer's absolute base/token URL from the spec server as the only default makes a CLI instance-locked and un-mockable; base/token URL should be overridable and (for same-host OAuth) derivable — but NOT defaulted to base-host for split-host providers.
