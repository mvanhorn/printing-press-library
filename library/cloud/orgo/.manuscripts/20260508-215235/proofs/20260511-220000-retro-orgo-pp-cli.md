## Findings

### F1. Doctor probes `/`, reports Credentials: ok with invalid keys (assumption mismatch)

- **What happened:** `doctor` probed the API root (`/`) and reported "Credentials: ok (HTTP 404 from /, but auth was accepted)" with an invalid API key. The next real command (`workspaces list`) immediately returned `HTTP 401: Invalid API key`. Doctor's purpose is to catch this *before* the user runs a real command, and it didn't.
- **Scorer correct?** Not a scored dimension (doctor health is mostly structural).
- **Root cause:** `internal/cli/doctor.go` template emits `verifyPath := "/"` unconditionally. For APIs where the bare root 404s independent of auth, doctor's auth claim is non-discriminating.
- **Cross-API check:** Yes, recurs. Existing issue **#1118** already covers Zendesk subdomain (`/` is help center), Notion (`notion.so/` is marketing), Linear (`linear.app/` is dashboard behind a bot wall). This finding adds Orgo: `/api/` returns 404 from the API gateway regardless of auth.
- **Frequency:** every API where the base URL root isn't a routed authenticated endpoint
- **Fallback if not fixed:** users discover bad keys on their first real call; doctor's "is everything fine?" promise becomes a lie.
- **Worth a fix?** Already accepted as worth fixing — issue is OPEN with priority:P2. The proposed fix (verify-path resolver: spec extension → first auth-only GET → fallback to `/`) is good. My contribution is another vendor-specific repro.
- **Durable fix:** Comment on #1118 with the Orgo evidence so the maintainer can validate the fix against a 404-from-base-URL case (different from Cloudflare interstitial cases already in the issue body).
- **Test:** Positive: doctor with invalid key prints FAIL + HTTP 401. Negative: doctor with valid key prints OK without spurious HTTP errors.
- **Evidence:** Reproduced in this session both before and after the local PATCH(doctor-authenticated-probe) fix in `internal/cli/doctor.go:175`.
- **Related prior retros:** `none aligned` — #1118 is the open canonical issue; this is the first cross-vendor confirmation from Orgo's 404-from-`/api/` shape (not Cloudflare-fronted).

### F2. `--select id,name` returns `{}` against list-envelope responses (template gap)

- **What happened:** `orgo-pp-cli workspaces list --select id,name --agent` returned `"results": {}`. The real response shape is `{"projects": [...]}`. Selector heads (`id`, `name`) never matched the wrapper key (`projects`), so the entire result was filtered to nothing.
- **Scorer correct?** Not a scored dimension. This is a UX-level template bug.
- **Root cause:** `filterFieldsRec` in `internal/cli/helpers.go` template only retains top-level keys matching selector path heads. List-envelope shapes (`{<key>: [...]}`) don't match.
- **Cross-API check (Step B — 3 named APIs with evidence):**
  - **Stripe** — `GET /v1/customers` returns `{"object":"list","data":[...]}`; `--select id,email` would silently return `{}`.
  - **Notion** — `POST /v1/search` returns `{"object":"list","results":[...]}`; same failure.
  - **GitHub** — `GET /search/repositories` returns `{"total_count":N,"items":[...]}`; same failure.
  - **Orgo** — `GET /projects` returns `{"projects":[...]}`; reproduced this session.
- **Counter-check (Step C):** Could the fix hurt other shapes? The proposed fix only descends when no top-level keys match. Bare-array responses already worked (early return). Direct-object `{id:..., name:...}` unchanged. Dotted-path selection (`projects.id`) unchanged. Safe.
- **Step G adversarial:** Maintainer might say "the user can write `data.id,data.name`." Counter: agents can't reliably guess envelope shape from a one-line help string, and `--select id,name` silently returning `{}` looks like a CLI defect. The fix raises the floor without breaking precise selection.
- **Frequency:** every API with envelope-wrapped list responses (the vast majority of paginated REST APIs)
- **Fallback:** users would have to either know the envelope key (CLI dependent) or skip `--select` entirely. Most agents will just stop using `--select`, defeating its purpose.
- **Worth a fix?** Yes — high frequency, safe fix, raises floor for every printed CLI.
- **Durable fix:** In `filterFieldsRec`, after the normal matching pass, if **no** top-level keys matched AND the object has array-valued fields, recurse into those arrays with the original paths; preserve non-array fields verbatim. (Already implemented locally — see `internal/cli/helpers.go:490`.)
- **Test:** Positive: `--select id,name` against `{"projects":[{"id":"a","name":"x","other":"y"}]}` → `{"projects":[{"id":"a","name":"x"}]}`. Negative: `--select id,name` against `{"id":"a","name":"b","other":"c"}` → `{"id":"a","name":"b"}` (direct object, unchanged); dotted form `--select projects.id` still works.
- **Evidence:** Reproduced in this session at `internal/cli/helpers.go` filterFieldsRec; fix landed as PATCH(select-envelope-descent).
- **Related prior retros:** none found.

### F3. Response cache key omits credentials — leaks across API keys (security/correctness bug)

- **What happened:** After running `workspaces list` with a valid key (populates the response cache), repeating the same path with an invalid key was served the cached good-key response. Exit code 0, `meta.source = "live"` claim, real workspace data leaked to a holder of a bad key. Same logic also serves cross-key cache hits between different valid keys testing in the same environment.
- **Scorer correct?** Not a scored dimension.
- **Root cause:** `Client.cacheKey()` in `internal/client/client.go` template was `sha256(path + map-iterated params)`. Two problems:
  1. Credentials weren't part of the key — different keys shared cache buckets.
  2. Map iteration order is non-deterministic in Go — identical requests with multiple params could compute different keys run-to-run.
- **Cross-API check (Step B):**
  - **Stripe** — test-mode and live-mode keys access different data; cross-key cache leak would surface the wrong account's data.
  - **Linear** — team-scoped API keys access different team data; same risk.
  - **GitHub** — PAT vs OAuth token for different users on a shared dev box; cache leak between users.
  - **Orgo** — multi-tenant; reproduced this session.
- **Counter-check (Step C):** Does including auth in the key hurt anything? It increases the number of cache files linearly with distinct keys seen. For the default 5-minute TTL, that's bounded. No correctness downside. The only "hurt" case is a user who *wants* caches to share — but I can't think of a real workflow where that's desired.
- **Step G adversarial:** Maintainer might say "users shouldn't rotate keys mid-cache-TTL." Counter: this is a data-disclosure bug, not a UX preference. Stripe documents the failure mode for their official SDKs (test/live key swap). The fix is small, safe, and a security improvement. Case-against is weak.
- **Frequency:** every printed CLI with the response cache (the standard generated client template includes it)
- **Fallback:** users have to remember `--no-cache` when switching keys or testing — easy to forget; also requires the user to know the cache exists. Bad default.
- **Worth a fix?** Yes — security, low complexity, high frequency.
- **Durable fix:** `cacheKey()` should append a SHA-256 fingerprint of `c.Config.AuthHeader()` to the key (first 4-8 hex chars, doesn't reveal the key) and sort params before hashing. (Already implemented locally — see `internal/client/client.go:92` PATCH(cache-key-auth-fingerprint).)
- **Test:** Positive: two clients with different `ORGO_API_KEY` values compute different cache keys for identical path+params. Negative: same key + same params → same key across runs (verify map-iteration determinism). Negative: bad key + populated cache from good key → cache miss → live API → 401 → exit 4.
- **Evidence:** Reproduced and fixed during this session.
- **Related prior retros:** searched #1126 (`HTTP cache RemoveAll wipes sibling state`) and #1131 (`Cache freshness helper`) — both touch the cache subsystem but neither addresses the key construction. No collision.

### F4. README Quick Start example uses non-existent flag name (default gap)

- **What happened:** Generated README example for `computers create` used `--workspace prod`. The actual generated flag from the OpenAPI parameter `workspace_id` is `--workspace-id`. Copy-paste of the Quick Start fails with `Error: unknown flag: --workspace`.
- **Scorer correct?** Yes, README scored 8/10 — this gap is consistent with that score. The scorer just doesn't drill into flag-name correctness.
- **Root cause:** README template appears to use a natural-language paraphrase of the parameter name rather than the actual kebab-case flag derived from the spec.
- **Cross-API check:**
  - Any CLI with snake_case body/query params that the CLI converts to kebab-case flags. Stripe (`payment_intent`, `customer_id`), Notion (`parent_id`), GitHub (`per_page`, `created_after`), and so on.
  - Hard to name three specific README example *failures* without checking each generated README — but the structural template gap is real.
- **Counter-check (Step C):** Would a fix hurt? No — deriving examples from the actual cobra flag set can only improve accuracy.
- **Step G adversarial:** Maintainer might say "this is a single CLI typo." Counter: it was generated, not authored. Every CLI with non-trivial flag renames likely has this. Case-against is weak.
- **Frequency:** most CLIs (any with non-identity flag-name transformation)
- **Fallback:** every first-time user trips on at least one Quick Start example until they consult `--help`. Erodes initial trust.
- **Worth a fix?** Yes, but P3 — narrow scope, cosmetic.
- **Durable fix:** README template should derive example flags from the actual cobra command's flag set (or apply the same kebab-case transformation the command uses). A post-gen lint that asserts every flag mentioned in README appears in `--help` output would catch this for every printed CLI.
- **Test:** Positive: regen a CLI with a renamed param; README's Quick Start uses the new flag name. Negative: post-gen lint fails CI when a README example uses a non-existent flag.
- **Evidence:** Reproduced this session; fix landed as PATCH(readme-workspace-id-flag).
- **Related prior retros:** none found.

### F5. (Skipped) `publish package` assumes `module <cli-name>` in go.mod

- **What happened:** `printing-press publish package` failed with `rewriting module path: go.mod does not contain expected module path "orgo-pp-cli"`. Our library copy had `module github.com/nickvasilescu/orgo-pp-cli` (a personal-fork-style path); the rewriter assumed the bare `module orgo-pp-cli` form.
- **Why skipped:** Step B couldn't name three APIs with evidence — most users don't customize the module path before publish, so the failure is rare. The "fix" is either a better error message or making the rewriter read the current go.mod and rewrite from that. Both improvements are small and worthwhile but the cross-CLI frequency doesn't justify a P1/P2 retro entry.
- **Step G:** Case-against is stronger — this is closer to user error (manually edited go.mod) than a generator gap. The unfriendly error is a small UX bug, not a systemic finding.
- **Workaround used:** Temp-cloned library to `/tmp/orgo-prep-publish`, rewrote go.mod and imports to bare form, packaged from there.

### F6. `.printer` manifest field empty when `git config github.user` was unset at print time (skill instruction gap)

- **What happened:** `publish validate` passed, but the publish skill's strict check (`PRINTER=$(jq -r '.printer // ""' ...)`) blocked because the manifest had `printer_name: "NickVasilescu"` but no `printer` field. Had to manually `jq '.printer = "NickVasilescu"'` three copies of the manifest.
- **Scorer correct?** Not a scored dimension.
- **Root cause:** At print time, `git config github.user` was unset; PP wrote `printer_name` (probably from `git config user.name`) but not `printer`. Setting `github.user` later doesn't backfill the manifest.
- **Cross-API check:** Every first-time user of `printing-press` whose `git config github.user` is unset. Existing issue **#1124** (`auto-derive printer from gh whoami when git config github.user is unset`) is OPEN with priority:P2 — same root cause.
- **Durable fix:** Already proposed in #1124: chain `--printer` flag → `git config github.user` → `gh api user --jq .login` → manifest `owner`. My case adds one new data point: even when the user *does* set `git config github.user` later, the manifest for an existing run stays broken. Suggest either a `publish` flag like `--auto-fill-printer` or a deferred fallback at publish-time (read `gh api user` if manifest's `printer` is empty).
- **Related prior retros:** `aligned` — #1124 is the canonical open issue. My comment adds the "manifest already shipped" failure mode.

## Work Units

### WU-1: Response cache key includes credential fingerprint (from F3)
- **Priority:** P1
- **Component:** generator
- **Goal:** Different API credentials get different cache buckets so bad keys can't be served good-key data; same credential + same params yields a stable key across runs.
- **Target:** `Client.cacheKey()` in the generated `internal/client/client.go` template.
- **Acceptance criteria:**
  - positive test: two clients with distinct auth headers compute different keys for the same path+params
  - positive test: same client, same path+params yields the same key across runs (no map-iteration non-determinism)
  - negative test: cache hit/miss behavior unchanged when only one credential is in play
- **Scope boundary:** Just `cacheKey()` — don't touch `readCache` / `writeCache` / TTL behavior.
- **Dependencies:** none
- **Complexity:** small

### WU-2: `--select` descends into list envelopes (from F2)
- **Priority:** P2
- **Component:** generator
- **Goal:** `--select id,name` against a list-envelope response (e.g. `{"projects":[...]}`) returns the envelope with each item projected to the selected fields, instead of `{}`.
- **Target:** `filterFieldsRec` in the generated `internal/cli/helpers.go` template.
- **Acceptance criteria:**
  - positive: `--select id,name` against `{"projects":[{"id":"a","name":"x","other":"y"}]}` → `{"projects":[{"id":"a","name":"x"}]}`
  - positive: `--select id,name` against `{"id":"a","name":"b","other":"c"}` (direct object) → `{"id":"a","name":"b"}` (unchanged)
  - positive: dotted-path selection `--select projects.id` still works
  - positive: bare-array response `[{...},{...}]` with `--select id` still works
  - negative: when top-level keys *do* match selector heads, no descent into nested arrays
- **Scope boundary:** Just the no-match envelope-descent fallback. Don't touch the dotted-path / array-element / object cases.
- **Dependencies:** none
- **Complexity:** small

### WU-3: README templates derive Quick Start example flags from actual cobra flag names (from F4)
- **Priority:** P3
- **Component:** generator
- **Goal:** Every flag mentioned in a generated README's Quick Start exists in the CLI's `--help` output.
- **Target:** README template generation; optionally a post-gen lint asserting flag-mention validity.
- **Acceptance criteria:**
  - positive: regen a CLI whose OpenAPI parameter is `workspace_id`; README example uses `--workspace-id`
  - positive: post-gen lint passes for all current library CLIs
  - negative: deliberately introducing a non-existent flag mention in README triggers the lint
- **Scope boundary:** Just example-flag derivation/validation. Don't restructure README layout.
- **Dependencies:** none
- **Complexity:** medium
