# BMW CarData — Novel-Features Brainstorm (audit trail)

Source: Phase 1.5c.5 subagent (delegate). First print (no prior research). Brief contained `## Codebase Intelligence` (source f ON), no `## User Vision` (source e OFF).

## Customer model

**Lena — the Home-Assistant EV efficiency nerd.** EU BMW iX owner, runs HA, obsessed with SoC, real-world range, charge cost.
- Today: locked into kvanbiesen/bmw-cardata-ha (~19K LOC Python); data trapped in HA; ~50/day rate limit silently burns.
- Weekly ritual: check SoC trend; reconcile charging sessions against electricity bill.
- Frustration: telemetry trapped in HA; no trends/cost; rate-limit budget invisible.

**Marco — the data-sovereignty tinkerer / fleet-of-one.** Owns a BMW + a MINI (multi-brand), EU Data Act "it's my data" framing, hoards Customer Archive .zip bundles.
- Today: downloads archive .zip, hand-parses KeyList.xml, spreadsheet; no side-by-side compare.
- Weekly ritual: pull fresh data, track km + energy across both vehicles.
- Frustration: no multi-VIN/fleet view; archive is one-shot XML; tjamet CLI has no store/create/analytics.

**Tomas — the live-stream hacker / MQTT bridge builder.** Pipes live telemetry into Grafana / custom dashboard.
- Today: runs dj0abr/bmw-mqtt-bridge (C++) or whi-tw (Python); ephemeral, no snapshot history.
- Weekly ritual: watch stream, debug state transitions.
- Frustration: stream write-only-to-the-wind; no stored snapshots, no diff; polling history eats quota.

## Survivors (8 transcendence, all hand-code)

| # | Feature | Command | Score | Buildability | Persona | Why Only We Can Do This | Long Description |
|---|---------|---------|-------|--------------|---------|------------------------|------------------|
| 1 | SoC/range trends | `soc-trends <vin> [--window 7d\|30d]` | 10/10 | hand-code `// pp:data-source local` | Lena | Joins telematic_snapshots (SoC descriptors) over time in SQLite + hintIfStale; derived range as column | Use for SoC and derived range as a numeric series over time. For capacity degradation vs nameplate use `battery-health`; for monetary charging cost use `charging-cost`. |
| 2 | Fleet status | `fleet status` | 9/10 | hand-code `// pp:data-source local` | Marco | Cross-join vehicles × latest telematic_snapshots per VIN into one table | Multi-VIN current snapshot across all mapped vehicles. For a single VIN's history over time use `soc-trends`. |
| 3 | Snapshot diff | `vehicles diff <vin> [--since <dur>]` | 7/10 | hand-code `// pp:data-source local` | Tomas | Compares two stored snapshots field-by-field — only possible with retained history | Discrete state changes between two snapshots. For a numeric level series over time use `soc-trends`. |
| 4 | Descriptor search | `descriptors search "<pattern>"` | 8/10 | hand-code `// pp:novel-static-reference` + `// pp:data-source local` | Marco/Lena | FTS over seeded VSS descriptor catalogue (path, unit, domain) | none |
| 5 | Charging cost & efficiency | `charging-cost <vin> --tariff <per-kwh>` | 10/10 | hand-code `// pp:data-source local` | Lena | Joins charging_sessions (kWh, duration) × energy × user tariff; DC efficiency per session | Monetary cost and DC efficiency of charging sessions (requires --tariff). For SoC level trends use `soc-trends`. |
| 6 | Quota tracker | `quota` | 10/10 | hand-code `// pp:data-source computed` | all | Local computed counter from sync metadata: used vs ~50/day + UTC-reset time | Shows the daily API budget remaining and UTC-reset time. To actually spend budget fetching data use `sync`. |
| 7 | Battery health | `battery-health <vin>` | 8/10 | hand-code `// pp:data-source local` | Lena | Joins basicData.hvsMaxEnergyAbsolute (nameplate) × max observed energy in history → degradation % | Capacity degradation (observed vs nameplate). For SoC level over time use `soc-trends`. |
| 8 | Trip reconstruction | `trips <vin>` | 7/10 | hand-code `// pp:data-source local` | Marco/Tomas | Segments navigation.currentLocation breadcrumb time-series into trips (start/end/elapsed/distance) | none |
