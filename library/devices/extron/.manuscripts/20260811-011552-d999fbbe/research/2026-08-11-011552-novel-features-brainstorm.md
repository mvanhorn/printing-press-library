# Extron Literature Library CLI — Novel Features Brainstorm

## Customer model

Personas are drawn from the on-disk brief's Users (AV integrators and field techs, system programmers, facilities AV operators, automation/agent power users) and Top Workflows, mapped onto the literature-library surface (spec sheets, user manuals, design/product guides, Declarations of Conformity, Revit BIM families) with the operative integrator workflows named in the task context: rack builds, firmware updates, quoting, commissioning.

1. **Maya Chen — AV Integration Lead / Systems Designer.** *Today:* assembling a bid for a corporate lobby refresh; pulling current spec sheets for DTP/MAV/DVS gear, input/output specs for the proposal, Declarations of Conformity for the compliance submittal, and Revit families for the consultant's building model. *Weekly ritual:* checks the Extron literature library for updated manuals and design guides on the products she specs, downloads them to the project share, and updates the project doc binder. *Frustration:* extron.com is browsable only by letter/category in a browser, the library is huge, and she manually re-checks each product page to see whether a manual got a new revision — the share drive is full of stale PDFs whose rev she can't verify.

2. **Danny Ortiz — Field Commissioning Tech.** *Today:* commissioning a DTP2 system on site; needs the latest user manual and control/design reference for the exact models on the job, on a laptop that may be offline. *Weekly ritual:* before each install he downloads manuals and firmware-era release notes for the job's model list and keeps a local mirror. *Frustration:* PDFs sit behind a WAF that blocks plain curl, the site's search-as-you-type is gated, and there is no offline way to know whether the manual he has matches the installed firmware rev — he runs on whatever got cached.

3. **Priya Raghavan — Facilities AV Manager.** *Today:* an instructor's room is down; she needs the user manual for the switcher in room 302 and the DoC for the maintenance file. *Weekly ritual:* maintains a doc library across the rooms she manages and checks for manual/firmware-update notices. *Frustration:* user manuals are buried under marketing pages, her rooms span many gear generations, and tracking which manual covers which device is a manual spreadsheet exercise.

4. **Alex Morgan — Control Systems Programmer / Automation.** *Today:* writing ControlScript/Global Scripter (and Q-SYS/Crestron) control code; needs the SIS command reference, user manual, and design guide per device family in machine-readable form. *Weekly ritual:* syncs a catalog of literature so scripts and AI-assisted ops can look up "what docs exist for this model and rev" without hitting the website. *Frustration:* literature is published as human-targeted PDFs with no structured listing he can query; he wants the synced catalog and JSON-shaped answers, not a browser tab.

## Candidates (pre-cut)

No `## User Vision` and no `## Codebase Intelligence` in the brief, so no (e)/(f) sources; all candidates are (a) persona-driven, (b) service-specific content patterns (the six literature.aspx categories and Rev/Date/Size columns), or (c) cross-entity local queries over the synced catalog. None re-propose the inline absorb manifest (`literature list`, `literature download`, `search`, `literature get`).

1. **Revision drift check** — `literature updates` — Reports which downloaded docs have a newer revision available in the synced catalog, by comparing local rev vs catalog Rev. Persona: Danny, Priya. Source: (a)+(c). Checks: no LLM (exact rev comparison), local data only, verifiable against catalog — passes.
2. **Library what's-new** — `literature recent` — Newest documents across the whole synced library ordered by the Date column, filterable by category and `--days`. Persona: Danny (firmware/manual tracking), Maya. Source: (b). Checks: passes. Long Description: scope redirect — do NOT use for your local docs' drift; use `literature updates`.
3. **Doc-set completeness** — `catalog completeness` — Per-model gap report across the six categories (Brochure / DoC / Design Guide / Product Guide / Manual / Revit BIM): which doc types each model in your downloads (or a `--bom` list) is missing. Persona: Maya (quoting/compliance), Priya. Source: (c). Checks: passes. Long Description: scope redirect — for a single model's doc list use `literature get`.
4. **BOM doc bundle** — `literature rack --bom <file>` — Reads a rack bill of materials (list of model numbers), resolves each model through the local catalog, and reports or downloads each model's full doc set. Persona: Maya (rack builds/quoting). Source: (a). Checks: passes; feasibility 1 (BOM parsing of arbitrary model-number formats).
5. **Series grouping** — `literature family <series>` — All docs for a product family (DTP, MAV, IPL, DVS…) by mechanical prefix matching of curated family tokens against catalog Description. Persona: Alex, Danny. Source: (b)+(c). Checks: near-LLM (grouping) — reframed as mechanical curated-prefix string match, no NLP — passes.
6. **Download integrity** — `catalog verify` — Compares local PDF sizes and revs against catalog Size/Rev metadata to flag truncated or mismatched downloads. Persona: Danny. Source: (c). Checks: passes; pain speculative (no direct truncation evidence).
7. **Revit BIM fetch** — `literature revit <model>` — Download the Revit family file for a model (service-specific content type used in building documentation). Persona: Maya. Source: (b). Checks: passes kill-checks but is a thin category filter over `literature download` — cut in Pass 3.
8. **Catalog stats** — `catalog stats` — Per-category counts and total sizes. Persona: Priya. Source: (c). Checks: FAILS scope-creep (dashboard-y aggregation with no action); cut.
9. **Superseded-rev cleanup** — `catalog prune` — Delete locally superseded revisions. Persona: Priya. Source: (a)+(c). Checks: useful but belongs as a flag on `literature updates` (`--prune`); cut as standalone.
10. **Compliance DoC** — `literature doc <model>` — Pull the Declaration of Conformity for a model (bid compliance submittals). Persona: Maya. Source: (b). Checks: thin category filter over `literature get`; cut.
11. **Catalog export** — `catalog export` — CSV/JSON dump of the synced catalog. Persona: Priya, Maya. Source: (c). Checks: FAILS user pain (trivial dump, low value); cut.
12. **Category-scoped search** — `literature search --type manual` — FTS scoped by category/type. Persona: all. Source: (c). Checks: re-proposes manifest `search` with flags; cut.
13. **Doc age report** — `literature age` — Days-since-Date per doc to spot stale manuals. Persona: Priya. Source: (b)+(c). Checks: covered by `literature recent` / list Date sort; cut.
14. **Local file lookup** — `catalog find <model>` — Show where each downloaded doc lives on disk. Persona: Priya. Source: (c). Checks: trivial path listing already implicit in `literature list`/`download`; cut.

## Survivors and kills

### Survivors

| # | Feature | Command | Score | Buildability | How It Works | Evidence | Long Description |
|---|---------|---------|-------|--------------|--------------|----------|------------------|
| 1 | Revision drift check (Danny, Priya) | `literature updates` | 9/10 | hand-code | Joins the local `files` table (revision parsed from the revision-aware filenames) against the synced `catalog` table's Rev column in local SQLite and lists docs where local_rev < catalog_rev — no external calls needed. | Brief: revision-aware download filenames + the local-catalog-with-revision-metadata thesis; domain memory: integrators keep stale PDFs on project shares with no way to detect drift. | Use this to find which downloaded docs need re-downloading. Do NOT use it to browse brand-new library arrivals — use `literature recent`. |
| 2 | Doc-set completeness (Maya) | `catalog completeness` | 8/10 | hand-code | Groups the synced catalog by model and cross-tabs the six categories (Brochure / DoC / Design Guide / Product Guide / Manual / Revit BIM) to report which doc types each model in your downloads (or a `--bom` list) is missing — a pure local SQLite query. | Brief Users (quoting/compliance for AV integrators); API spec: the six literature.aspx categories are a service-specific content pattern. | Use this to find which doc types are missing per model for bids/commissioning. Do NOT use it for a single model's doc list — use `literature get`. |
| 3 | Library what's-new (Danny, Maya) | `literature recent` | 7/10 | hand-code | Queries the synced `catalog` table ordered by the Date column with `--days`/`--category` filters to list the newest literature across the whole library, fully offline. | API spec: the literature.aspx table exposes a Date column not surfaced elsewhere; domain memory: firmware/manual update tracking is an integrator workflow. | Use this to track what Extron released recently across the library. Do NOT use it for the drift of your own downloads — use `literature updates`. |
| 4 | BOM doc bundle (Maya) | `literature rack --bom <file>` | 7/10 | hand-code | Reads a rack BOM file of model numbers and resolves each model through the same local catalog data `literature get` uses, then reports or batch-downloads each model's full doc set — local orchestration over real catalog data. | Task context names rack builds/quoting as the operative integrator workflow; brief Top Workflows are fleet/project-shaped batch operations. | Use this to assemble doc sets for an entire rack at once. Do NOT use it for a single model — use `literature get`. |
| 5 | Series grouping (Alex, Danny) | `literature family <series>` | 6/10 | hand-code | Matches the catalog Description field against a small curated list of mechanical family prefixes (DTP, MAV, IPL, DVS, PCS, …) to group all docs for one product series — a local SQLite query with string-prefix matching, no NLP. | API spec: catalog titles embed model names and are indexed only by first letter on the site, so cross-letter series browsing is a real gap; brief device families (MAV/DTP/DVS) are the prefix vocabulary. | Use this to browse every doc for a product family across letters. Do NOT use it for a single model's official docs — use `literature get`. |
| 6 | Download integrity (Danny) | `catalog verify` | 6/10 | hand-code | Joins local PDF file sizes and filename revisions against the catalog's Size and Rev columns to flag mismatches or truncated downloads — local data only. | API spec: Size/Rev metadata per row plus WAF-gated transport that makes downloads the flaky leg of the pipeline; brief's dry-run/batch download makes integrity a follow-on need. | none |
