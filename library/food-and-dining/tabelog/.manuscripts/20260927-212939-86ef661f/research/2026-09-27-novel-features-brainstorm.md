## Customer model

### The returning Japan trip planner

**Today (without this CLI):** The planner revisits Tabelog restaurant and bar pages across several planning sessions, comparing neighborhoods, cuisine, ratings and meal budgets. Candidates and personal reasons for choosing them have to be retained separately from the source pages. This model comes from the brief's Users section, “Trip planning sessions” workflow, and the user's explicit approval of named saved lists, notes and offline comparison.

**Weekly ritual:** During an active planning period, build and revisit lists such as Kyoto dinners and Tokyo bars, add candidates, record personal notes, and compare the same places before making choices. The brief establishes repeated planning sessions; this is a planning-week ritual, not a claim of year-round weekly use.

**Frustration:** Reconstructing the same shortlist and its personal context every time the source tabs are reopened.

### The traveler choosing the next meal

**Today (without this CLI):** The traveler opens several venue pages to check location, hours, access, payment and reservation information, then returns to earlier candidates when the first choice is unsuitable. The brief links firsthand location-browsing friction at https://www.reddit.com/r/JapanTravelTips/comments/1d8ob21/ and explicitly distinguishes nearest-station distance from distance to the traveler.

**Weekly ritual:** During the trip, revisit saved candidates, check practical source facts, refresh retrieved information before relying on it, and choose a plausible backup in the same source area when needed.

**Frustration:** Repeating practical checks across separate pages while losing track of which facts are missing or old.

### The agent assembling a factual meal shortlist

**Today (without this CLI):** The agent resolves places and cuisines, reads search results, and opens selected detail pages before explaining options. It has to track source URLs, retrieval times, missing facts and distinct lunch/dinner budgets in conversation context. The brief's “Cheap progressive discovery” and “Evidence-based alternatives” workflows require small outputs and selective detail retrieval; its linked rating discussions document confusion about what scores and sorting mean.

**Weekly ritual:** Across the traveler's planning sessions and trip, produce a short factual comparison, inspect only the candidates that need deeper evidence, and revisit saved choices without recreating the entire search.

**Frustration:** Repeatedly transferring and reconciling the same facts while avoiding unsupported claims about quality, cost, opening times or availability.

1. **Trip notebook.** **Weekly use:** Yes during the repeated planning sessions established in Top workflow 2: the planner saves, annotates and resumes the shortlist. **Wrapper versus leverage:** It is not a rename of a source endpoint; the source has no approved unauthenticated endpoint for the user's trip notes and local memberships. **Transcendence proof:** SQLite joins preserve personal trip context alongside source snapshots while remaining useful offline. **Sibling kill:** Account list synchronization was killed because it requires an unestablished authenticated write surface; the local notebook meets the approved need. **Buildability:** `hand-code`—write a small cohesive Cobra `lists` group, shared SQLite membership/note helpers and root wiring; basic show/note/remove lifecycle operations belong to this feature and are not additional transcendence rows. Adding an unseen ID must return an actionable “fetch this restaurant first” error rather than creating fake restaurant facts. **Long-description validity:** Its named sibling `lists refresh` survives with that exact name.

2. **Offline decision comparison.** **Weekly use:** Yes: the planner and agent revisit the same candidates across planning sessions and meal choices. **Wrapper versus leverage:** It joins multiple saved venues and personal notes into one decision surface; no single detail response supplies that result. **Transcendence proof:** SQLite supplies the multi-venue join, while agent-shaped output preserves complete identity, exact meal/budget provenance, unknown values and retrieval age. **Sibling kill:** A lunch-versus-dinner savings command is a duplicate view of this comparison, and its stronger savings claim is not supported. **Buildability:** `hand-code`—one local query plus typed comparison rendering and Cobra/root wiring, reusing existing field/projection machinery. Fetch no missing details automatically; annotate “not fetched” separately from “source unknown.” Show source rating and review count without a composite score. **Long-description validity:** Its named sibling `lists alternatives` survives with that exact name.

3. **Explicit refresh with fact changes.** **Weekly use:** Yes during planning and travel: Top workflow 3 specifically calls for refreshing saved facts before reliance. **Wrapper versus leverage:** A direct detail request neither selects a saved group nor compares old/new fields, preserves user context or reports partial failure against the previous valid data. **Transcendence proof:** Source-to-SQLite comparison produces an explicit change set and a durable result across intermittent source failures. **Sibling kill:** A historical timeline adds retention and temporal-query scope for an occasional use; the current refresh can show the changes relevant to the next decision without building an archive. **Buildability:** `hand-code`—bounded detail retrieval through the established source adapter, typed old/new comparison and safe persistence, plus Cobra/root wiring. Retain only the bounded current/prior state needed for the operation; no scheduled polling. Compare the same semantic fields and budget provenance; classify newly fetched evidence as added evidence rather than a proven real-world change. A successfully refreshed record may have source-unknown fields; never carry an old field forward disguised as current. Preserve the complete last valid snapshot for a failed record and return visible per-ID failures with non-success command status for a partial failure. **Long-description validity:** Its named sibling `lists audit` survives with that exact name.

4. **Evidence-matched saved alternatives.** **Weekly use:** Yes during active meal planning and travel: each original choice can need a backup, matching the brief's named alternatives ritual. This is useful within the saved shortlist, not a claim to find every suitable restaurant. **Wrapper versus leverage:** It performs an anchor-to-candidate join over user-selected entities with explicit acceptance reasons; no source endpoint represents that saved-trip comparison. **Transcendence proof:** SQLite joins source identity, exact categories, list membership and optional meal brackets into explainable candidates. **Sibling kill:** The open-now/bookable picker was killed because the source data cannot support current availability; matching stored facts is useful and verifiable within the approved scope. **Buildability:** `hand-code`—one bounded local comparison over saved structs plus typed output and Cobra/root wiring. Same area means equal canonical verified prefecture/area route identifiers, not station proximity or an inferred radius; missing/invalid area provenance is unevaluable. Category matching is exact normalized source-label overlap, with no NLP. The required `--match` argument explicitly selects the anchor fields to match from the small validated set `area,category`; a caller must supply at least one matching constraint, and output echoes the active constraints. The example asks for both. The optional budget test requires an explicit meal and a known source bracket upper bound at or below the caller's yen threshold; call it a cached-bracket test, not a live source filter or guaranteed bill. Report unmatched/unevaluable counts and reasons, exclude the anchor by source ID, expose source URLs and ages, label any displayed station distance `nearest_station_distance_m` without interpreting it as distance from the traveler, and preserve stable list order rather than inventing a recommendation score. **Long-description validity:** Its named sibling `lists compare` survives with that exact name.

5. **Evidence and freshness audit.** **Weekly use:** Yes for the agent's repeated planning sessions and on-trip checks: it chooses which of several saved candidates actually needs a detail request before producing an answer. **Wrapper versus leverage:** No remote endpoint knows the local snapshot age, required evidence set or whether the user has fetched a detail section. **Transcendence proof:** A local provenance/field join turns missing-data distinctions into bounded, actionable candidate IDs while avoiding detail fan-out. **Sibling kill:** The readiness score hides exactly which fact is missing and encourages unsupported confidence; the audit reports the underlying states. **Buildability:** `hand-code`—one local scan of required fields, provenance and timestamps plus Cobra/root wiring. Required fields are a small validated enumeration, not an expression language. Output distinguishes `detail_not_fetched`, `source_unknown`, and `older_than_threshold`; a present reservation-policy field is not a seat-availability result. `source_unknown` must not promise that another refresh will resolve it. `--max-age 0` disables age warnings/checks while retaining missing-evidence findings. **Long-description validity:** Its named sibling `lists refresh` survives with that exact name.

Shared implementation constraints for these five survivors:

- Declare exactly one data-source directive in each handwritten command source. Notebook operations, comparison, alternatives and audit use `// pp:data-source local` and reject `--data-source live` with a clear “no live equivalent” error. Refresh uses `// pp:data-source live` because it requires a remote fetch and rejects `--data-source local` with “no local data source for refresh”; the local selection and previous snapshot are its inputs, not an offline refresh substitute. None silently falls back to stale facts while reporting a successful live update.
- Before returning local restaurant results, call the generated hint helpers against the normalized restaurant resource: `if !hintIfUnsynced(cmd, db, "restaurants") { hintIfStale(cmd, db, "restaurants", flags.maxAge) }`. If the integration gives this normalized resource a different name, use that exact registered name consistently. Hints remain on stderr; structured provenance remains in stdout. `--max-age 0` disables stale-read hints. Empty local state is an empty saved/fetched scope, not evidence of no restaurants at the destination.
- Drain every SQLite result set into plain structs, check `rows.Err()`, and close rows before any follow-up ID resolution, child expansion, source retrieval or second query. A single-connection SQLite store must never retain open parent rows while issuing a follow-up query.
- Write list metadata and restaurant updates through the same `*sql.Tx` where atomicity is required, or commit the custom-table transaction before calling pooled `store.Upsert`/`store.UpsertBatch` helpers. Never nest those helpers inside an open custom write transaction; propagate all upsert failures. Source parsing must complete and validate before a refreshed record can replace its previous snapshot.
- Reuse the approved direct-HTTP adapter and normalized field/rendering model. The source has no authentication in the established contract, so no new credential path is needed. Bound refresh venue count, concurrency, total timeout and body size; deduplicate selected IDs; do not extend this into automatic crawling. Keep all five workflows under the cohesive `lists` group.
- Verify through executable fixtures and store-backed workflows: save/note/restart/read offline; compare source facts and unknowns; filter alternatives with one matching, one mismatched and one unknown candidate; distinguish unfetched/source-unknown/stale audit findings; refresh changed records while retaining failed records and notes. These establish useful behavior without tests that merely mirror implementation.
