# Ori CLI Brief

## API Identity
- Domain: Local-ops control plane for the openclaw-a2a-server JSON-RPC bridge.
  The server is launchd-managed (`dev.error2.openclaw-a2a-server`), binds
  `localhost:8788`, and fronts two A2A agents (`ori`, `adam`) configured via
  `~/.openclaw/agents.toml`.
- Users: Single power user (Elad, senior dev, home-lab operator). No public
  users, no SaaS surface, no rate limits.
- Data profile: Agent task transcripts (one row per task), task-state
  transitions, accumulated agent response text, approval requests. All small,
  structured, FTS-able.

## Reachability Risk
- None. Server is up: `GET /healthz` → 200, `GET /.well-known/agents.json` →
  `{"agents":["ori","adam"]}`. Confirmed via direct probe at 2026-05-15-23:01.
- Single failure mode: post-`compose-down/up` the launchd bridge needs
  `launchctl kickstart -k gui/$(id -u)/dev.error2.openclaw-a2a-server` or
  `chat_*` returns empty `failed`. This is exactly the kind of operational
  ritual the CLI should collapse into one verb.

## Top Workflows
1. **Dispatch a task to ori or adam** without going through Claude Code's MCP
   tools (`chat_ori`, `chat_adam`) — direct shell access, scriptable, agent-
   composable.
2. **Resume a wedged task by id** — when the main Claude context overflowed
   and the bridge returned `failed`, reattach via task_id to retrieve the
   accumulated agent output.
3. **List in-flight tasks across both agents** — current state of the world,
   filterable by `--agent`, `--state`, `--since`, `--context`.
4. **Search past task transcripts** — FTS5 across cached agent responses, e.g.
   "what did I have ori work on related to kanban hygiene this week".
5. **Approvals pending across both agents** — single-pane-of-glass list, then
   approve/deny by id.
6. **Doctor / kickstart** — recover from the bridge-wedge state and surrounding
   stack failures (plugin cache TTL env vars, OAuth refresh, gateway healthz)
   in one command.

## Table Stakes
- Everything that `mcp-a2a-bridge` exposes today: chat, resume, cancel,
  list_tasks, approvals_list, approvals_respond — per agent.
- Compatible with the existing agent identities (ori, adam) and contexts.
- Streaming/SSE consumption for `chat` (mirror agent card's `streaming: true`
  capability).
- Honor `input_required` state for tools that pause for user input — surface
  the input prompt to stdout/stderr in non-MCP mode.

## Data Layer
- Primary entities:
  - **tasks**: task_id, context_id, agent, state, text, created_at, updated_at,
    turn_count
  - **agents**: name, version, description, capabilities (streaming, approvals)
  - **approvals**: approval_id, task_id, agent, summary, requested_at, context,
    decided_at, decision, reason
  - **contexts**: context_id, agent, first_task_id, last_task_id, started_at,
    last_activity_at, label (user-assigned)
- Sync cursor: A2A server's `ListTasks` is the source of truth; sync pulls
  all tasks per agent, upserts by task_id. Approvals follow the same pattern
  per agent.
- FTS5: index `tasks.text` (accumulated agent response) and
  `approvals.summary`. Search query format: standard FTS5 with prefix +
  near-match support.

## Codebase Intelligence
- **A2A server source**: `/Users/i347208/dev/openclaw-a2a-server`, FastAPI/Starlette
  on uvicorn, port 8788, JSON-RPC 2.0 dispatch (single POST per agent).
- **Bridge source**: `/Users/i347208/dev/mcp-a2a-bridge`, Python MCP server using
  the A2A SDK client. Multi-agent mode emits per-agent suffixed tools
  (`chat_<agent>`).
- **Agent config**: `~/.openclaw/agents.toml` declares `[agents.ori]` and
  `[agents.adam]` with URLs and `supports_approvals: true`.
- **Auth**: localhost loopback. Server supports optional bearer via
  `A2A_AUTH_TOKEN_FILE`; current deployment leaves it off. CLI sets
  `OPENCLAW_A2A_TOKEN` if the user later enables it.
- **Architecture**: A2A protocol uses protobuf messages over JSON-RPC, with
  SSE-backed streaming for `SendMessage` / `SubscribeToTask`. The CLI client
  package translates REST-style calls (per this spec) into the underlying
  JSON-RPC dispatch.

## User Vision
- Replace the per-agent MCP tool sprawl (`chat_ori`, `chat_adam`, `resume_ori`,
  `cancel_adam`, ...) with one CLI that has a unified verb-noun shape
  (`ori chat <agent>`, `ori tasks list --agent ori`).
- Add value the bridge cannot: local SQLite task history + FTS5 search, a
  `doctor` command for the recurring stack diagnostics, a `kickstart` command
  for the launchd dance, and a cross-agent `approvals pending` view.
- The CLI's MCP server (auto-generated by the press from the Cobra tree)
  becomes the eventual replacement for mcp-a2a-bridge — same surface plus the
  transcendence features.

## Product Thesis
- Name: **Ori** (note: shares the name with the primary agent — intentional;
  the CLI is the user-facing surface and the agent is one of its targets).
- Why it should exist: The current Claude Code experience requires invoking
  per-agent MCP tools through the chat surface. Shell access bypasses Claude
  Code entirely, scripts can compose it (`ori tasks list --json | jq`),
  cron can run periodic `ori doctor`, and a local SQLite mirror unlocks
  retrospective queries the bridge cannot answer ("show me every task that
  hit `input_required` in the last 7 days").

## Build Priorities
1. **P0 (foundation)** — SQLite store for tasks, agents, approvals, contexts;
   sync command that paginates `ListTasks` across both agents; FTS5 search
   across `tasks.text` and `approvals.summary`.
2. **P1 (absorbed)** — All bridge MCP tools, matched and beaten:
   - `ori chat <agent> "..."` (replaces `chat_ori`/`chat_adam`)
   - `ori chat <agent> --context <id>` (resume by context, MCP bridge doesn't expose this directly)
   - `ori tasks list --agent <name> [--state running|completed|...] [--since 24h]`
   - `ori tasks get <task_id> --agent <name>`
   - `ori tasks cancel <task_id> --agent <name>`
   - `ori tasks resume <task_id> --agent <name>` (replaces `resume_ori`)
   - `ori approvals list [--agent <name>]` (defaults to all agents)
   - `ori approvals respond <approval_id> --decision approve|deny [--reason]`
   - `ori agents list` (replaces direct `/.well-known/agents.json` fetch)
   - `ori agents get <name>` (capability inspection)
3. **P2 (transcendence)** — Commands that only work because of the SQLite
   mirror + cross-agent view + shell access:
   - `ori doctor` — runs every health check in one verb (launchd bridge
     status, `/healthz` reachability, both agents responding, plugin cache
     env vars commented in compose, agents.toml valid, codex OAuth fresh).
   - `ori kickstart` — `launchctl kickstart -k gui/$(id -u)/dev.error2.openclaw-a2a-server`
     plus a post-kickstart `/healthz` poll with timeout.
   - `ori sync` — paginate `ListTasks` for every configured agent, upsert
     into the local store, refresh approvals.
   - `ori tasks search <query>` — FTS5 across cached task text. Supports
     `--agent`, `--since`, `--state`, prints task_id + agent + first matching
     line.
   - `ori contexts list` — derive conversation contexts from cached tasks
     (group by context_id, show first/last activity, task count).
   - `ori logs tail [--stream stdout|stderr] [--lines N]` — tail
     `~/Library/Logs/openclaw-a2a-server/{stdout,stderr}.log` without
     remembering the path.
   - `ori watch` — long-running watcher that polls `ListTasks` every N
     seconds, shows state transitions live, useful for "is ori still
     working".
