# Novel-Features Brainstorm — priority-pp-cli (subagent audit trail)

## Customer model

**Dana — integration developer at a Priority channel partner.** *Today (without this CLI):* Dana maintains nightly sync and EDI jobs for six customer tenants. She has Postman collections per tenant, a hand-rolled Node throttler that sleeps between calls to stay under 100/min, and a wiki page of which forms are API-licensed on which install. When a bulk `$batch` load half-fails (no rollback), she diffs response JSON by hand to figure out which of the 100 ops landed. *Weekly ritual:* verify last night's `$since` pulls completed for every tenant, re-run failed bulk loads, and pre-flight any new form she is about to integrate. *Frustration:* a half-failed batch leaves the ERP in an unknown state and she has no journal of what succeeded; verifying "did my sync actually get everything" is guesswork because OData here has no `$count`.

**Rivka — AR/collections analyst at a mid-size manufacturer.** *Today:* Rivka lives in the Priority UI and a Power BI OData feed that refreshes twice a day. Before each collections call she opens four screens: customer card, open invoices, order backlog, last payments. The assafch MCP proves her workflow matters — 7 of its 72 tools are AR — but she has no terminal-speed way to get one customer's whole picture. *Weekly ritual:* Monday collections review — aging buckets, top debtors, then per-customer deep dives for the call list. *Frustration:* assembling a single customer's 360 view (balance, aging, open orders, last invoice) takes four separate lookups and burns her patience and the 100/min cap.

**Amir — order desk / operations lead.** *Today:* Amir triages orders and stock in the Priority UI: pending orders in one tab, WARHSBAL in another, LOGPART lookups in a third. He cannot answer "which parts will we run out of given the open order book" without exporting to Excel and doing a VLOOKUP between order lines and stock. *Weekly ritual:* Monday shortage triage — walk open orders, check stock coverage, decide what to expedite from open POs. *Frustration:* the demand-vs-stock join across ORDERITEMS, LOGPART, and PORDERS exists in no screen and no API call; it is a manual spreadsheet every single week.

**Maya — AI-agent builder wiring Priority into automations.** *Today:* Maya builds agents (MCP/n8n) against customer tenants where every install has custom `ORGT_` fields and differently-licensed forms. Her agents discover schema by trial-and-error GETs — burning the rate limit — and break after tenant upgrades change fields silently. *Weekly ritual:* onboarding or re-grounding an agent on a tenant: find the right form, find the field names on THIS install, confirm the form is API-licensed, test a write. *Frustration:* schema archaeology against a >10MB EDMX with per-tenant variance, and no way to know what changed after an upgrade except when the agent starts 400ing.

## Survivors and kills

Pass 3 interrogation, per survivor:

- **C1 forms search** — Weekly: yes, Maya re-grounds agents on tenants weekly and Dana pre-flights new forms. Wrapper: no — no API endpoint searches metadata; it queries the local parsed-EDMX cache. Transcendence: local SQLite metadata cache over a >10MB EDMX. Sibling killed: C11 field usage (project-phase cadence). Buildability: hand-code. Long refs: `search` — survives (manifest #18).
- **C2 forms diff** — Weekly: yes during integration projects (pre-deploy drift check across six tenants); upgrade-time spikes on top. Wrapper: no. Transcendence: snapshot store in SQLite; service-specific per-install variance pattern. Sibling killed: C11. Buildability: hand-code. Long refs: `forms search` — survives.
- **C3 forms licensed** — Weekly: yes for Maya (every agent onboarding) and Dana (every new form integration); verdicts cached so repeats are free. Wrapper: no single endpoint exists — it is a probe protocol plus a local verdict cache. Transcendence: service-specific content pattern (per-form API licensing, the #1 in-the-wild failure per the brief). Sibling killed: C14 error explainer. Buildability: hand-code. Long: none.
- **C5 batch resume** — Weekly: yes, Dana's bulk loads run nightly and partial failures are routine with no rollback. Wrapper: no — journal + selective re-submission is pure leverage over `$batch`. Transcendence: local SQLite journal exploiting the documented no-rollback pattern. Sibling killed: C13 rate-plan estimator (a flag, folded into batch). Buildability: hand-code. Long refs: `batch` — survives (manifest #8).
- **C6 reconcile** — Weekly: yes, "did the nightly sync get everything" is Dana's Monday question. Wrapper: no — there is no `$count`; this is a windowed probe strategy joined against local row counts. Transcendence: cross-source (local SQLite vs live) computed check. Sibling killed: C4 write ledger (misleading partial data). Buildability: hand-code. Long refs: `sync` — survives (manifest #29).
- **C7 shortage** — Weekly: yes, Amir's Monday shortage triage is currently an Excel VLOOKUP. Wrapper: no API call can express this join. Transcendence: three-table local join (order lines, parts, open POs). Sibling killed: C10 dead stock (monthly cadence, weaker join). Buildability: hand-code. Long refs: `stock --below-min` — survives (manifest #25).
- **C8 customer summary** — Weekly: yes, every collections call list. Wrapper: no — four lookups collapsed into one local join. Transcendence: cross-entity local join + agent-shaped single-customer payload. Sibling killed: C12 cashflow (table-stakes overlap, speculative data quality). Buildability: hand-code. Long refs: `debtors`, aging — both survive (manifest #19/#20).
