# WooCommerce CLI Brief

## API Identity

- **Domain:** E-commerce store management. WooCommerce is the WordPress e-commerce plugin — the most-deployed store platform on the web (millions of live stores).
- **Critical structural fact:** there is **no global API host**. The API is *per-store*, served by each merchant's own WordPress install at `https://<store>/wp-json/`. The CLI must be pointed at a store URL (`WOOCOMMERCE_BASE_URL`, or `base_url` in config). This shapes everything — onboarding, doctor, multi-store support.
- **Two distinct namespaces, and this is the whole thesis:**

  | Namespace | Auth | Scope | Verified |
  |---|---|---|---|
  | `wc/v3` (Admin API) | consumer key + secret | Full store CRUD: orders, products, customers, coupons, refunds, taxes, webhooks, settings | 401 without creds, confirmed live |
  | `wc/store/v1` (Store API) | **none** | Public read-only catalog: products, categories, tags, brands, attributes, reviews, aggregate collection data | 200 with real data, confirmed live |

  The Store API being public means the CLI can read **any WooCommerce store on the internet** with zero credentials. No existing WooCommerce tool exploits this.
- **Users:** store owners/operators, agencies managing client stores, developers integrating WooCommerce, and (new, via Store API) anyone doing competitive catalog research.
- **Data profile:** orders (high volume, time-series, the gravity center), products + variations (medium volume, mutable, price/stock churn), customers (medium, slow-changing), coupons/taxes/shipping/settings (low volume, config-like).

## Reachability Risk

- **None.** Verified live against `woocommerce.com`, which is itself a production WooCommerce store:
  - `GET https://woocommerce.com/wp-json/wc/v3` → **200**, returns the complete machine-readable route index, no auth required.
  - `GET https://woocommerce.com/wp-json/wc/store/v1/products?per_page=1` → **200**, real product JSON, no auth. `x-wp-total: 1676`.
  - `GET https://woocommerce.com/wp-json/wc/v3/products?per_page=1` → **401** `woocommerce_rest_cannot_view` — the expected, correct auth boundary.
- Probe-safe endpoint: `GET /wc/v3` (documented as requiring no authentication; used as `health_check_path`).
- **Known environment hazards** (not API blocks, but real deployment friction worth surfacing in `doctor`):
  - Some hosts/mod_security strip the `Authorization` header, producing a misleading "Consumer key is missing" error over SSL. WooCommerce's documented workaround is passing `consumer_key`/`consumer_secret` as query parameters.
  - ModSecurity can return `501 Method Not Implemented` on PUT/DELETE.
  - Pretty permalinks must be enabled or `/wp-json/` routes 404 entirely.
- No rate-limit headers observed on the Store API (`cache-control: max-age=60`, CDN-cached). WooCommerce core ships no request throttling by default; Store API rate limiting exists but is opt-in per store.

## Spec Source Decision

Researched exhaustively — findings:

- **No official OpenAPI/Swagger spec exists.** Automattic publishes hand-written Slate docs only. Not on apis.guru (confirmed by grepping the full 8.8MB list).
- Best community spec: `wtx-labs/woocommerce-api-openapi-specification` (OpenAPI 3.0.1, 12 stars, updated 2026-02-17) — **67 paths**, missing `/data`, Order Actions, and Product Custom Fields.
- Store API: **no machine-readable spec exists anywhere** (confirmed — only PHP schema classes in the monorepo).

**Chosen source: the live WP-REST route index**, captured from `woocommerce.com`:
- `GET /wp-json/wc/v3` → 204 routes → **96 after filtering to WooCommerce core** (excluding WooPayments, Marketplace, PayPal, Subscriptions and other plugin routes present on that particular store).
- `GET /wp-json/wc/store/v1` → 31 routes → **11 read-only catalog routes** selected.

This beats every published alternative: ~107 endpoints vs 67, it is generated by the server itself rather than transcribed, and every argument arrives with live `type`, `default`, `required`, `enum`, and `description` (verified: all 24 args on `GET /wc/v3/orders` carry descriptions and full status enums). It is also the only viable source for the Store API half.

Cross-checked against the official Slate docs (33 documented resource groups, 140 endpoint declarations) — the live index is a superset; the docs are stale relative to shipped code (e.g. `orders/statuses`, `products/related`, `products/brands`, global `variations` are live but undocumented).

## Top Workflows

1. **Daily order operations** — what came in, what's stuck, what needs fulfilling, what got refunded.
2. **Catalog + inventory management** — bulk price/stock edits, find what's out of stock or mispriced, audit catalog completeness.
3. **Customer & revenue analysis** — who buys repeatedly, what's the LTV, which products drive revenue vs. refunds.
4. **Competitive catalog research** *(only possible via the public Store API)* — track any competitor's WooCommerce catalog, pricing, and sale cadence over time.
5. **Store diagnostics** — is the API reachable, do my keys work, what extensions/routes does this store expose, why is this endpoint failing.

## Competitive Landscape

Surveyed exhaustively across GitHub, npm, PyPI, crates.io, pkg.go.dev, and Homebrew.

- **There is no mature third-party WooCommerce CLI.** The `woocommerce-cli` GitHub topic is empty — zero repos have ever used it. No Homebrew formula exists. Every Go WooCommerce package found (`hiscaler/woocommerce-go`, `dinistavares/go-woocommerce-api`, `mikespook/wc-api-golang`, and four others) is SDK-only: no `cmd/`, no Cobra, no shipped binary. The field is genuinely open.
- **The real third-party CLIs are tiny and single-purpose:** `order-fetcher` (2★, order→CSV extraction with SKU filters and multi-host config), `woco` (2★, bulk product upload), `wpscrape` (1★, unauthenticated Store API scraping — products/categories/site only), `WooPriceUpdater` (0★, Excel price sync), `shopextract` (1★, multi-platform snapshot/changes/history/compare). Three more repos (`sendanor/woocommerce-cli` from 2015, `magebean/woobean-cli`, `getoladius/oladius`) were announced and **never implemented** — empty repos.
- **WP-CLI's native `wc` bridge is weaker than it looks.** It dynamically maps REST routes to commands, but the source hardcodes `$target_rest_version = 'v2'` — it targets the *older* `wc/v2` namespace, never `v3`. It also blacklists `settings`, `system_status`, `system_status/tools`, and all `reports` routes from CLI generation, and skips every `batch` route. And it requires shell access to the WordPress host. A `wc/v3` CLI is ahead of it on API currency, surface, and reach on day one.
- **The energy went into MCP servers, not CLIs.** A dozen-plus exist, all stateless live-API proxies. `AmitGurbani/mcp-server-woocommerce` has the most complete surface (101 tools) with 1 star; `techspawn` has 96 stars. Feature completeness and adoption are uncorrelated here.
- **Automattic's own `woocommerce/woocommerce-claude`** (24★, framed as an experiment) is the real quality bar. It competes on *18 analytics workflow skills* — catalog-audit, refund-triage, inventory-risk-review, coupon-performance-triage, customer-value-review, failed-order-triage, revenue-drop-triage, weekly-store-review, tax-reconciliation and more — not on CRUD count. WooCommerce core also ships a native MCP in developer preview (WC 10.3+) that is deliberately narrow: product and order CRUD only.

**What nobody has:** not one tool persists store data locally. Every competitor asks the API one question at a time, which is precisely why they all inherit the Reports API's structural limits. And apart from `wpscrape`'s three read commands, nobody exploits the unauthenticated Store API — so nobody can look at a store they don't own.

## Table Stakes

Every competing tool must be matched:
- Full CRUD across all core resources (orders, products, variations, customers, coupons, categories, tags, attributes, reviews, taxes, shipping zones/methods, webhooks, settings, payment gateways, system status).
- Batch operations (`/batch` exists on most resources — create/update/delete in one request).
- Filtering and pagination on list endpoints (`per_page`, `page`, `offset`, `after`/`before`, `status`, `search`, `orderby`).
- Reports: sales, top sellers, and the five `*/totals` endpoints.
- Webhook management.

## Data Layer

- **Primary entities:** `orders` (with line items), `products`, `variations`, `customers`, `coupons`, `refunds`, `categories`, `reviews`.
- **Sync cursor:** `modified_after` / `after` (ISO8601) on orders and products — the API supports incremental pulls natively. `dates_are_gmt` matters for correctness.
- **FTS/search:** product name/SKU/description, customer name/email, order number/customer, review content.
- **Why local storage is decisive:** the WooCommerce Reports API is thin (totals, sales, top sellers). It cannot answer cohort retention, LTV, repeat-purchase rate, refund rate by product, stockout velocity, gateway failure rates, or price history — all of which are trivial once orders/products/customers are joined in SQLite. It also has no cross-store capability at all.

## Known Correctness Traps (must get right)

1. **Store API prices are in minor units.** `{"price":"4900","currency_minor_unit":2}` means $49.00. Naive tools display 4900. The CLI must normalize using the per-response `currency_minor_unit`.
2. **Admin API prices are decimal strings** (`"49.00"`) — different convention in the *same CLI*. Both must be handled.
3. Monetary amounts are strings, not numbers; item counts are integers. Blank fields come back as `null` or `""`, not omitted.
4. Pagination totals live only in `X-WP-Total` / `X-WP-TotalPages` headers — invisible if you only parse the body.
5. Default `per_page` is 10 and is capped at 100.

## Product Thesis

- **Name:** `woocommerce-pp-cli`
- **Why it should exist:** Every existing WooCommerce tool is a thin HTTP wrapper that assumes you own the store and asks the API one question at a time. This CLI is the only one that (a) mirrors the store into local SQLite so it can answer the compound merchant questions the Reports API structurally cannot, and (b) exploits the public Store API so it works against *any* WooCommerce store with no credentials at all — turning a store-management tool into a market-research tool.

## Build Priorities

1. Data layer + sync for orders, products, variations, customers, coupons, refunds — the foundation every novel feature depends on.
2. Full absorbed CRUD surface across all core resources, agent-native (`--json`, `--select`, `--dry-run`, typed exit codes).
3. Transcendence commands: the compound local queries and the public-store competitive intelligence.
4. Correct money handling and store-capability introspection as first-class, verified behavior.
