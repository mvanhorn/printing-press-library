# Printing Press Retro: etsy (Etsy Open API v3)

## Session Stats
- **API:** Etsy Open API v3. 77 paths and 107 operations; auth uses an `x-api-key` header plus OAuth2 PKCE.
- **Spec source:** official OpenAPI 3.0.2 (public). Generation used an overlay for resources, auth and sync hints.
- **Scorecard:** 96/100 (Grade A).
- **Verify pass rate:** 100% (159/159).
- **Live dogfood:** 192/192 executed rows passed in the final run.
- **Fix loops:** shipcheck ran 11 times, and the local peer-review gate ran 9 rounds.
- **Manual code edits:**
  - many deliberate `// etsy-ext:` patches in generated files, recorded in `.printing-press-patches/`;
  - about 20 hand-authored files.
- **Features built from scratch:** 15 novel features, including shop audits, money reports, market research and bulk edit. The run also built a hand MCP buyer-data boundary.
- **Version:** cli-printing-press v4.35.6.

## Findings

### 1. `lock promote` Path A still deletes the library `.git`, including on a first print (Bug)
- **What happened:** `lock promote --cli etsy-pp-cli --dir <working copy>` succeeded. It created `~/printing-press/library/etsy` with no `.git`. The working copy held a 146-commit local build history, and that history did not reach the library. It was recovered only from a manual pre-promote tar backup.
- **Scorer correct?** N/A.
- **Root cause:** `internal/pipeline/lock.go`.
  - The staging copy goes through `CopyDir`, and `copyDirFiltered` in `publish.go` drops every `.git`.
  - `moveGitMetadataIntoPromotedLibrary` runs only under `if sameTarget`, which is the in-place/Path B case.
  - On Path A, the existing library `.git` is removed along with the `.old` backup.
  - On a first print the working-dir `.git` is never carried over.
- **Cross-API check:** this is independent of the API. #4587 documents it on seats-aero, splitwise and ticketmaster; the ticketmaster library's first commit is a "RECOVERY baseline". It is now reproduced on etsy at v4.35.6, on a first print.
- **Frequency:** every Path A promote where the library or working dir carries local git history.
- **Fallback if the Printing Press doesn't fix it:** the operator must remember to back up `.git` before every promote. Forgetting loses the only copy of local build history: library repos are local-only and have no remote by design.
- **Worth a Printing Press fix?** Yes. This is silent data loss, and it regressed or was never fixed for Path A after #4587 was closed.
- **Inherent or fixable:** fixable.
- **Durable fix:**
  - On Path A, preserve the target library's existing `.git` across the swap: move it into staging before the rename, as the sameTarget path does.
  - On a first print, carry the working dir's `.git` into the new library when the library has none.
  - Keep #1304's guarantee that `.git` never enters a *publish* package.
- **Test:**
  - Positive: a Path A promote over a library with `.git` keeps HEAD and commit count, and a first-print promote from a working dir with `.git` produces a library with that history.
  - Negative: `publish package` output still contains no `.git`.
- **Evidence:** the etsy run's Phase 20. The memory note records this as the 4th reproduction.
- **Related prior retros:** a prior workshop retro (splitwise / seats-aero) is `aligned`. #4587 (closed) and #4038 (closed) are the prior issues; their fix appears to cover only the sameTarget path.

### 2. The generated learn loop and generic MCP tools have no data-sensitivity control (Missing scaffolding)
- **What happened:**
  - The generated post-sync lookup refresh extracts name-like tokens from all synced resource types into `entity_lookups`. This includes personal-data types such as buyer receipts and addresses.
  - The generic MCP `sql` tool can read `entity_lookups` and the learn tables (`search_learnings`, `learn_candidates`, `learning_playbooks`, `learn_recall_misses`).
  - `learnings list` emits stored `query_pattern` and `resource_id`.
  - `recall` dereferences resource rows (`validateResource`).
  - An MCP agent therefore reached personal data through four distinct paths. The etsy run closed them one per peer-review round, with hand `etsy-ext` patches to six generated files plus a conformance test.
- **Scorer correct?** N/A.
- **Root cause:** generator templates.
  - `sync.go.tmpl` `refreshLookupsFromSyncedStore` and `learn_lookups/store.go.tmpl` `collectSyncedCandidates` read `SELECT resource_type, data FROM resources` over every type.
  - `mcp_tools.go.tmpl` `validateReadOnlyQuery` checks statement shape only and has no table scope.
  - `learnings.go.tmpl` and `learn/recall.go.tmpl` have no sensitivity filter.
  - `LearnConfig` has no field for sensitive resource types. The only opt-out is `learn.disabled`, which is all-or-nothing.
- **Cross-API check:** every learn-loop CLI has the pattern. That is etsy, splitwise (its store holds user `email`/`first_name`, and the same `validateReadOnlyQuery` gate is in `internal/mcp/tools.go`) and seats-aero (same refresh and `sql`). Any future store-backed CLI over personal data inherits it.
- **Frequency:** a subclass, namely store-backed CLIs whose synced resources include personal data (orders, users, contacts, messages).
- **Fallback if the Printing Press doesn't fix it:** hand-patching generated files. That is not regen-durable without patch records, and it is easy to get partially right; the etsy run needed 4 rounds to find every path.
- **Worth a Printing Press fix?** Yes. MCP agents can be prompt-injected, and there is no generator-level way to keep chosen resource types out of derived tables and agent surfaces short of disabling learning entirely.
- **Case against filing, and why it fails:** "It is the operator's own data going to the operator's own agent." It fails because the data is third parties' (buyers'), and the agent surface is not trusted input. The workshop's privacy and security lenses rated it Medium in 3 consecutive rounds.
- **Inherent or fixable:** fixable.
- **Durable fix:**
  - Add a spec- or overlay-level sensitivity marker, e.g. `x-pp-sensitive: true` on a resource, or a `learn.sensitive_resource_types` list.
  - Have the generator honour it in four places: the lookup extract (skip), `sql` (a TEMP VIEW / table scope over `resources` and derived tables), `learnings`/`recall` output (drop or redact), and `search`.
  - Add an opt-in env override. The etsy patches are a working reference: an allowlist, TEMP views, an extract filter and a conformance walk.
  - Uncertainty: the marker could live in the spec overlay or the profiler could infer PII-shaped fields. The overlay is cheaper and explicit, so prefer it.
- **Test:**
  - Positive: a spec marking a type sensitive yields no rows of that type via MCP `sql`, `search`, `learnings list` or `recall` without the override.
  - Negative: unmarked types behave exactly as today.
- **Evidence:** etsy peer-review rounds 2, 3, 5 and 8. Each round found another bypass path.
- **Related prior retros:** none. #4556 (closed) is `extends`: it fixed teach-log redaction, not data sensitivity.

### 3. Generated MCP tests fail when the CLI's API-key env var is set (Bug)
- **What happened:** with the operator's real `ETSY_API_KEY` exported, the hermetic gate failed, and therefore so did Phase 10 validate. `TestMCPSearchMissingStoreIsActionable` and `TestMCPSQLMissingStoreIsActionable` assert a `data.db` path, but the credential-scoped store path becomes `data-<hash>.db`. The run had to add `env -u <KEY>` to every test invocation.
- **Scorer correct?** N/A.
- **Root cause:**
  - The generator template `cliutil_testenv.go.tmpl` `clearedVars` clears config, data and XDG variables but not the auth env var(s).
  - `helpers.go.tmpl` `defaultDBPathInDir` scopes the DB by credential.
  - `mcp_tools_test.go.tmpl` asserts the unscoped name.
- **Cross-API check:** the same generated tests ship in splitwise and seats-aero (`internal/mcp/tools_test.go`). Any CLI whose operator keeps the key exported, which is the normal setup, hits this.
- **Frequency:** every CLI with credential-scoped stores, on an operator machine with credentials set.
- **Fallback if the Printing Press doesn't fix it:** agents misread it as a code defect, or wrap every test run in `env -u`.
- **Worth a Printing Press fix?** Yes. It blocks a shipping gate for a reason unrelated to the CLI.
- **Inherent or fixable:** fixable.
- **Durable fix:**
  - Have `testenv.Isolate` also clear the CLI's declared auth env vars (from `x-auth-env-vars` / the manifest).
  - Alternatively, have the missing-store tests derive the expected path through `defaultDBPath()` instead of hard-coding `data.db`.
  - Sub-item: the newer `cliutil_darwin_acl_live_test.go.tmpl` calls bare `chmod`, which fails when GNU coreutils is first on PATH; use `/bin/chmod`. Only etsy has that test so far, which is why it is a sub-item and not its own finding.
- **Test:**
  - Positive: with the auth env var exported, `go test ./internal/mcp/...` passes.
  - Negative: the intentional scoped-path test still passes and still sees the scoped name.
- **Evidence:** etsy Phase 10 validate failure. Every later gate in the run used `env -u ETSY_API_KEY -u ETSY_SHARED_SECRET -u ETSY_SHOP_ID`.
- **Related prior retros:** none.

### 4. Live-dogfood stdin rules are undocumented in the build skill (Skill instruction gap) — comment on the existing issue
- **What happened:**
  - To give a file-input novel command a real happy path, the run switched it to `pp:happy-stdin`. The runner then rejected a YAML fixture, because `json.Valid` requires JSON.
  - It also appended `--stdin` to the argv, and the command had no such flag.
  - Each discovery cost a full live dogfood run.
- **Root cause:** `skills/printing-press/phases/11-build-the-goat.md` mentions `pp:happy-stdin` only as an alternative to `pp:happy-args`. Only `docs/SPEC-EXTENSIONS.md` states the JSON rule, and nothing documents the auto-appended `--stdin`. The behaviour lives in `internal/pipeline/live_dogfood.go`: `json.Valid` at about line 2137, and `liveDogfoodAppendStdinArg`.
- **Disposition:** comment on open #4259 ("skill: live-dogfood coverage rules … undocumented") with these two specific rules, rather than file new.

## Anti-patterns
- **Reading only the verdict line of a live dogfood run.** PASS plus HOLLOW coverage looked like a gate mismatch (D9).
- **Fixing a privacy boundary one tool at a time.** This was the etsy F2 history. The durable answer was a conformance walk over the real tool list, plus an allowlist.
- **Making a 403 durable, then non-durable.** On a quota-capped dependent walk the settled design is one probe per run: a 403 recorded with no probe hid the scope problem, and an unrecorded 403 starved the walk.

## What the Printing Press Got Right
- **Hand edits are patch-recorded and regen-durable.** `// etsy-ext:` markers plus `.printing-press-patches/` records, enforced by a test, kept dozens of generated-file edits trackable.
- **The acceptance marker is bound to a source fingerprint** that covers only `.go`/`go.mod`/`go.sum`/spec. Doc and manuscript commits after the marker stay valid, and any code edit forces a fresh live run.
- **`blockedRootFlags` and the file-flag annotations in the cobratree mirror** are a solid MCP egress baseline.
- **The Phase 5 hollow-coverage gate** correctly refused to promote a CLI whose flagship paid/file-input commands had only dry-run coverage, which forced real happy paths.
- **The live dogfood matrix** (192 rows) plus `pp:preview-happy-path` gave real coverage of mutating commands without real writes.
