# G2 CLI Brief

## API Identity
- Domain: B2B software discovery, peer reviews, and buyer-intent intelligence. G2 is the largest software marketplace (150K+ products, 3M+ reviews, 2K+ categories). After the Feb 2026 acquisition, G2 + Capterra are one company.
- Users: SaaS sellers (PMM, growth, sales ops, competitive intel) who need to monitor reviews, watch competitors, score buyer intent, and operationalize G2 signals into CRM/marketing tooling. Buyers (procurement, IT) use the same surface to research and shortlist.
- Data profile: medium-volume, slow-moving entities (products, categories, vendors), high-volume slow-decay signals (reviews, buyer_intent visits, market_signals), and very-high-volume firehose data (per-visitor intent events, screenshots). Strong fit for a local-mirror + delta-sync model.

## Reachability Risk
- Medium. The official API exists and is OAuth 2.0 + AccountAPIToken, but:
  - Requires a paid G2 Sell-tier subscription (or "Marketing Solutions" plan) plus developer-portal app registration. Free tier exists at `my.g2.com/developers` with 1,000 API calls / month starter quota.
  - The visible OpenAPI surface is narrow: buyer_intent, screenshots, categories, market_signals, credit_account. Products/Reviews/Vendors live on a SEPARATE legacy "syndication" API (`/api/2018-01-01/syndication/...`) gated by a partner-issued `api_token` query param, not on `/api/v2/`.
  - The website itself is DataDome-protected (browser-sniff fails); the CLI MUST hit the official API.
  - Credit-based metering: G2 deducts credits per call (`/credit_account`, `/credit_deductions` endpoints exist to audit usage). Burst spending is real risk.
- Evidence: official docs at documentation.g2.com confirm OAuth + tiered access, the OpenAPI spec at `data.g2.com/openapi/v2.yaml` shows the narrow v2 surface, and the syndication endpoint pattern is documented under the partner docs.

## Spec source
- Best spec URL: `https://data.g2.com/openapi/v2.yaml` (OpenAPI 3.0 partial — covers buyer_intent, screenshots, categories, market_signals, credit_account). Use `--openapi` for these.
- Interactive reference: `https://data.g2.com/api/v2/docs/index.html`
- Docs URL (overview + auth + scopes): `https://documentation.g2.com/docs/g2-api`, `https://documentation.g2.com/docs/developer-portal`, `https://documentation.g2.com/docs/g2-api-information`
- Buyer intent reference: `https://documentation.g2.com/docs/buyer-intent-data-reference`
- Syndication (products / reviews / product_mappings / hashed_users — NOT in v2 OpenAPI): `https://documentation.g2.com/partners/docs/get-started-with-g2-review-syndication`. Base: `https://data.g2.com/api/2018-01-01/syndication/`. Auth: `api_token` query param.
- Postman/community spec: G2 maintains a public Postman workspace at `https://www.postman.com/g2-demo` (forkable collection for OAuth flow + `/api/v2/products` smoke test).
- Recommendation: hybrid generation. Use `--openapi` against `v2.yaml` for the modern endpoints; use `--docs` for the syndication API (products, reviews, product_mappings, hashed_users) — there is no public OpenAPI for the syndication surface.

## Top Workflows
1. Daily review pull for owned products with diff vs. yesterday: who reviewed, star delta, sentiment shift, new criticisms, syndication-eligible reviews. (Reads syndication/reviews.)
2. Buyer-intent triage: pull yesterday's high-intent companies, rank by score, enrich with firmographics already in payload, emit a CSV/JSON for the sales team or pipe into a CRM. (Reads `/api/v2/buyer_intent` + product-scoped variant.)
3. Competitive watch: track competitor products' rating trajectory, badge changes, and new reviews; alert on "your competitor just dropped 0.2 stars in Mid-Market" type signals. (Combines syndication/reviews on a competitor's product_id with category-level market_signals.)
4. Category share-of-voice: pull every product in a category, rank by review velocity and rating, identify rising challengers. (Categories + product features + per-product review counts.)
5. Local mirror with FTS: incrementally sync reviews into SQLite, run full-text search across years of review text, surface verbatims by feature, sentiment, segment.
6. Credit-budget telemetry: surface remaining monthly credits and per-endpoint spend so the user doesn't burn quota mid-month. (Reads `/credit_account` + `/credit_deductions`.)
7. Product mapping bootstrap: walk syndication/product_mappings to learn the G2 IDs for your catalog so review-pulls work; cache locally.

## Table Stakes (what competitors / community tools all have)
- OAuth-or-token auth with a `g2 auth login` flow that handles both AccountAPIToken and OAuth client-credentials.
- `g2 products list/show` and `g2 reviews list --product <slug-or-id>` even though those live on the syndication API, not v2 — users expect them.
- Pagination handling (page[size] + page[number] for syndication, separate cursor pattern for v2).
- JSON + table output, `--format json|table|csv`.
- Local cache to avoid re-hitting credit-metered endpoints.
- Buyer-intent listing scoped per product and globally.
- Category browse + drill into product features.

## Data Layer (entities for local SQLite)
- Primary entities:
  - `products` (id, slug, name, vendor_id, category_ids[], description, star_rating, review_count, updated_at) — backbone.
  - `reviews` (id, product_id, reviewer_hash, rating, title, body, pros, cons, criteria_ratings, submitted_at, segment, industry) — FTS5 indexed on title/body/pros/cons.
  - `categories` (id, slug, name, parent_id, hierarchy_path) — recursive.
  - `category_features` (category_id, feature_id, name, definition) and `product_features` (product_id, feature_id, mention_count, avg_rating).
  - `vendors` (id, name, hq, employees, products[]).
  - `buyer_intent_events` (subject_product_id, company_id, company_name, domain, employees, industry, country, region, page_type, visit_url, visited_on, last_seen_at, activity_level, buying_stage, signal_type) — high-volume, partition or sharded by month.
  - `market_signals` (category_id, date, intent_score, visits_count) — aggregated intent rollups.
  - `screenshots` (id, product_id, url, created_at).
  - `credit_ledger` (date, endpoint, calls, credits_used) — local mirror of `/credit_deductions` so users can see what burned the budget.
  - `product_mappings` (partner_product_id, g2_product_id, mapped_at) — syndication bootstrap.
  - `sync_state` (entity, last_synced_at, last_cursor, last_page) — drives delta sync.
- Sync cursor: syndication uses `page[number]` + `page[size]` (max 100) with `links.next`; v2 endpoints use `filter[created_at][gte]` / `filter[updated_at][gte]` plus pagination params. Persist last `updated_at` per entity for incremental pulls. Buyer intent uses `filter[visited_on][gte]` for delta.
- FTS/search candidates: review body, pros, cons, criticisms; product description and tagline; vendor description; category name/description. SQLite FTS5 with porter stemmer.

## User Pain Points
- API gated behind paid Sell-tier subscription; users want to see what data is actually behind their tier before paying. CLI should clearly distinguish "endpoint exists but you need scope X" vs "endpoint not entitled".
- Credit-based metering is opaque: most users learn they've burned the month's credits the hard way. No first-class spend telemetry in the dashboard. Big opening for the CLI.
- Two APIs (modern v2 OAuth and legacy syndication api_token) with different auth, pagination, and base URLs — confusing in practice. Users want one interface.
- Reviews API returns hashed users (`hashed_users`) — joining reviews back to identifiable people is intentionally hard. CLI should surface and explain this rather than appear "broken".
- Buyer intent paginates oddly (dimensions + measures + filters style, closer to an analytics API than REST); cursor handling is non-obvious.
- No native bulk export. Users build their own ETL. CLI's "sync to SQLite" is the high-value differentiator.
- Rate limits and 429s are not loudly documented; community reports indicate burst caps below the documented monthly credit count. Need retry-with-backoff baked in.
- No webhooks for new reviews / new buyer-intent. Users poll. CLI cron mode is valuable.
- DataDome blocks scraping the public site, so anyone wanting alt-tracking, comparison pages, or peer-listings is forced through the paid API or sketchy scrapers (Apify, RapidAPI scraper, biegehydra/Advanced-G2-Scraper).
- HN sentiment ("G2 is broken for IT decision making") notes G2's surface optimizes for sentiment, not technical fit — a CLI that lets a buyer pull review verbatims about latency / compliance / API limits across alternatives is real value.

## Codebase Intelligence
- Anthropic's hosted G2 MCP is closed-source, but its tool surface (visible in this env) is the single best public signal of what G2 exposes via OAuth. The 14 tools above map roughly to: products (4), categories (2), vendors (2), reviews (2), buyer_intent (3), competitive intel (1). A CLI that ships at least these as first-class commands beats every published competitor immediately.
- OpenAPI security schemes: `AccountAPIToken` (header) and `G2OAuth` with scopes `openid`, `profile`, `buyer_intent.read`, `screenshots.read`, `product_features.read`, `market_signals.read`. Expect additional scopes (`products.read`, `products.reviews.read`) to be assignable at app-registration time per the developer-portal docs, even if not in the visible YAML — register an app with all checkboxes to discover the full scope list.
- Syndication API uses `api_token` query parameter (NOT a header), and base path is dated (`/api/2018-01-01/syndication/...`). Generator must support BOTH auth modes.
- Buyer intent response is dimension-measure-filter style (more cube-like than REST). Generator should treat as a parameterized analytics call, not REST CRUD.
- All v2 responses are JSON:API formatted (`data`, `meta`, `links`); syndication is also JSON:API. Lean on a shared JSON:API client layer.

## Product Thesis
- Name: `g2-pp-cli`
- Why it should exist: Today the user's choices are (a) the closed Anthropic G2 MCP (chat-only, no bulk export, no cron, no local DB), (b) hand-rolled curl against two different G2 base URLs with two different auth schemes, or (c) ToS-violating scrapers. None give you a credit-aware local mirror with FTS, delta-sync, and a single command surface across both v2 and syndication APIs. A CLI that unifies the two APIs, mirrors entities into SQLite, FTS-indexes reviews, audits credit burn, and adds a cron-able buyer-intent triage flow is the missing piece between G2's data and a seller's daily workflow.

## Build Priorities
1. **Auth surface that handles both worlds** — `g2 auth login` supporting OAuth (client_id/secret) for v2 AND `api_token` for syndication, with `~/.config/g2-pp-cli/auth.json` storing both. Refresh-token rotation for OAuth.
2. **Local SQLite mirror with delta-sync** — `g2 sync products|reviews|categories|vendors|buyer_intent|market_signals|screenshots` with incremental `--since` and stored cursors in `sync_state`. FTS5 on review text. Default DB at `~/.local/share/g2-pp-cli/g2.db`.
3. **Credit-aware execution** — every command checks `/credit_account` first when `--credit-budget` is set; refuses to run if a sync would exceed remaining credits. `g2 credits` reports per-endpoint spend by day. This is the killer feature: nobody else surfaces this.
4. **Unified core commands** — `g2 products list/show`, `g2 reviews list --product`, `g2 categories tree`, `g2 vendors show`, `g2 buyer-intent list [--product] [--since]`, `g2 market-signals list --category`, `g2 screenshots list --product`. JSON + table + CSV output.
5. **Review FTS + analytics** — `g2 reviews search "<query>" [--product] [--segment] [--rating-lt 3]` over the local FTS index. `g2 reviews trend --product --by month` for rating over time, sentiment-by-feature breakdown.
6. **Buyer-intent triage** — `g2 intent triage --since 24h --min-score 50 --export csv` outputs a sales-ready list (company, domain, employees, industry, intent score, page type, signals seen). Cron-friendly; integrates with the locally mirrored `buyer_intent_events` table.
7. **Competitive watch** — `g2 watch --product <competitor-id>` polls reviews + market_signals and emits a diff (new reviews, rating delta, badge changes) since last run. Saves diffs to `~/.local/state/g2-pp-cli/diffs/`.
8. **Bootstrap helpers** — `g2 bootstrap` walks the user through OAuth app registration, scope selection, and initial product-mapping sync; `g2 doctor` validates auth, lists granted scopes, shows credit balance, and prints any 401/403/429 from a smoke-test.
9. **Cron mode** — `g2 cron install` writes a launchd/systemd unit for daily intent + review pulls; surfaces results via macOS Notification Center / desktop notification.
10. **Novel beyond table-stakes** — `g2 alt-track <my-product>` synthesizes "people considering me also considered X" from buyer-intent `signal_type=Alternatives` + competitor evaluation patterns, producing a ranked list of switching threats — something the website paywalls and no other tool exposes cleanly.
